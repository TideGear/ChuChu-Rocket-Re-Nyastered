# Audio: sources, playback and verification

Method: `tools/audio_compare.py` decodes the 15 mobile music files (Ogg Vorbis, mono, 44.1 kHz, ~48 kbps nominal; byte-identical in every
iOS build and in Android) and the Dreamcast CD audio tracks (raw PCM, stereo, 44.1 kHz), and correlates 10 Hz band-energy envelopes.

## Mapping (mobile file -> Dreamcast track)
M00->04, M01->05, M02->06, M03->07, M04->08, M05->09, M06->10, M07->11, M08->12, M09->13, M10->14, M11->15, M12->16, M13->17.
- Every Dreamcast track starts with **2.0 s of extra lead-in** compared with the mobile file (lengths differ by exactly 2.0 s for the 1x tracks).
- **M08, M09 and M11: the Dreamcast tracks are 4.02x longer** (327 s, 334 s, 372 s vs 81, 83, 93 s): the disc stores roughly four copies of the corresponding mobile-song material.
- **M14** (the Sonic Team splash jingle) is Dreamcast **track 18** (7.0 s = 2.0 s pre-gap + 5.0 s). The earlier envelope match to the end of track 04 was a coincidence of the same fanfare; the traced startup request and listening confirm track 18. Its CD repeat behavior is not established. The Dreamcast jingle is 4.35 s long, peak 15,983, RMS 1,682; the mobile clip is 4.03 s, peak 10,577, RMS 1,092 (3.7 dB quieter).
- Envelope correlations: 0.86-0.94 for tracks with clean matches (04, 05, 14, 17), lower (0.36-0.74) on short or sparse pieces where the metric is weak; the 2.0 s offset and the
  exact 4x/1x length ratios are the stronger evidence. The mobile files are the Dreamcast recordings, trimmed and re-encoded.
- Unmatched: Dreamcast track 02 (9 s, silent pre-gap then 7 s), probably a sting; no known call site or mobile counterpart yet.

## Conclusion
The Dreamcast CD audio is the **highest-quality music source** (lossless stereo; tracks 12, 13, and 15 contain four copies of their corresponding mobile-song material). Mobile files are a lower-fidelity re-encode of the same music. The port currently loops those tracks at the end of one mobile-file-length segment after the 2.0 s lead-in; whether and where the original CD driver loops them remains unverified.
SFX and voices (iOS/Android 52 effects, mono ~70 kbps; Dreamcast `DP2SOUND.MLT`, `VOICE.AFS`) are not compared yet.

## Original note-on and modulation setup (2026-11-18)

`tools/dc_sound_voices.py` reproduces complete allocator 0x16f0..0x1804 for 1..64 driver records: first zero header, priority eligibility and the exact byte-3/0x3e/0x3f candidate comparisons/ties. It returns raw status/voice/register addresses; `Allocation.index(count)` only identifies a consistent in-range slot. `dc_voice_allocation_probe.py <MANATEE.DRV>` executes the original routine in 14,406 generated cases, comparing all three returns and confirming voice records are unchanged. Cases include two-record boundaries, seeded 1/2/4/48/64-record tables, first-free slots and zero-low-RAM controls.

An original allocator edge remains relevant to integration: if the final nonfree record fails the incoming-priority comparison at 0x1734, r1 remains the priority byte rather than the saved-candidate address. Loads at 0x17f0/0x17f4 then read low RAM with ARM7 rotation. The model preserves these raw returns, rather than inventing a conventional allocation failure. The probe reports 4,795 non-voice returns, including 24 failure statuses, in these synthetic cases. This does not establish that gameplay reaches them. Zero enabled voices, live allocation/stealing timelines, and caller behavior after an out-of-range return still require tracing before integration.

`tools/oracle/dc_note_on_live_alloc_probe.py <MANATEE.DRV> <loaded.MLT> <state>... [--saturate]` runs complete original note-on 0xd68 with the captured voice table and count byte left in place, sweeping every populated controller with keys 36/60/96, velocities 1/100 and priorities 0/15/31. On 11 English captures (25,344 calls) the Python allocator's first pick is a changed record in all 25,212 calls that changed any voice; the other 132 changed nothing (no matching split). The caller treats r0==0 as success, then writes voice/channel/key fields and the register block through the returned pointers. `--saturate` fills every slot with randomized nonfree records: 1,257 of 2,304 calls allocate as modeled; 734 take the raw non-voice return and fault in Unicorn at 0xfb0/0xfec, immediately after the allocator. That is a Unicorn limit (only the 2 MB RAM and register windows are mapped), not evidence of hardware behavior. Across all 154 English captured states the driver uses at most 34 of 48 voices, so captured gameplay never reaches stealing or the raw-return edge. Delayed layers, drum exclusion groups and filter/mix controllers remain open.

`mlt_programs.split_matches` follows ARM 0xf3c..0xf70's inclusive note/velocity bounds. `matching_splits` returns ordered candidates per enabled layer; it does not assume allocation will accept the first candidate. ## Key-off cause and sample timing (2026-11-18)

Ordinary loop handling follows ARM 0x6e58..0x6edc. `SequenceClock` retains the opening marker, repeat count (zero means indefinite), traversal counter and encoded opening delay. A repeat uses that opening delay with any current closing-marker extension; finite exit uses the closing delay. The parser retains encoded/prefix components for loop markers. `dc_loop_probe.py` matches 40 generated finite/infinite cases (counts 0,1,2,3,127, both delay widths and prefixes on either marker), checking loop pointer/count fields as well as timing, commands and gates. All 17 DP2 music sequences pass the combined probe: eight through end, nine through two repeats each, totaling 238,409 updates, 42,064 semantic reads and 80,769 queued words. Use `dc_sequence_clock_probe.py ... --all --loop-passes 2` to reproduce. Context flag bit 1's alternate-sequence branch, active replacement, voice dispatch and audio remain open; repeated command checks do not prove audible music loops.

System-exclusive handling follows ARM 0x6d34..0x6dd8. The parser reads a 15-bit payload length, its step-width flag, payload and trailing delay; previously it mistook the first length byte for a step and the delay for an unknown field. ## Sampled-channel monitor reads (2026-11-19)

`SampledVoiceBank.read_arm` derives the pinned core's ReadCommonReg 0x2810/0x2811 and 0x2814/0x2815 paths. Byte selector 0x280d uses MSLC bits 0..5; reserved bit 7 is retained/ignored. Status combines AEG attenuation (values above 0x3bf return 0x1fff), two-bit envelope phase and the loop latch. A low-byte status read preserves the latch; a high-byte or whole-status read returns it and then clears it. ARM word reads zero-extend the halfword. Position reads return the low 16 bits of the current sample position, with the pinned-core compatibility clamp to LEA-3 when LEA>LSA and LEA>3. The source itself notes uncertainty about that clamp on real hardware. AFSEL=1 remains explicitly unsupported: the pinned core warns and substitutes AEG rather than implementing FEG monitoring. Unmodeled slots and other common/DSP accesses reject.

The reference patch adds opt-in FLYCAST_AICA_READS=<query.csv> plus FLYCAST_AICA_READS_OUT=<result.csv>. Query rows are sample(decimal),selector(hex),address(hex),width(decimal 1/2/4); output appends the hexadecimal value.
