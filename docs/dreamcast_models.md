# Dreamcast polygonal models (FOUND, 2026-11-12)

The retail disc's `DPMODEL/` folder is empty. The game models are Ninja *chunk* models compiled into `1ST_READ.BIN` (load base 0x8C010000, no NJCM headers).
`tools/dc_models.py` finds them by scanning for `NJS_CNK_MODEL` structs (vlist ptr, plist ptr, centre xyz, radius), validates the vertex chunks (types 32-50) and polygon chunks (materials 16-23, tiny textures 8/9, strips 64-75), and writes one OBJ per model plus `index.json`.

Result: 128 models in `1ST_READ.BIN` (`2_DP.BIN` contains none; its `/dptutor/model/*.nj` are loaded from other media). Contact sheet checked visually (`local/models_sheet.png`):
- #4 (0x778ac): 69-vertex character head, with the 24-frame vertex-morph table at 0x7ceb8 (frames = {ptr,index} pairs, stride 828 bytes);
- #12-20: big-eared mouse body, 96 vertices, 8 animation variants;
- #26, #33, #44, #57...: small gems/spheres/pickups; #63-78: round-bodied "chao"-style special characters (2 sets, with and without wings);
- #84-89: rockets with exhaust fins; #80-83: quarter-sphere/tile pieces; #97: sphere; #90-96, #98+: flat quads (planes, shadows, UI polys).

Still to do: the object hierarchy (NJS_CNK_OBJECT: eval flags, pos/ang/scale, child/sibling) to assemble multi-part characters, texture-id to PVR mapping (texids 16384.. = 0x4000 | index, per-model texture lists), morph animation playback, and model-to-gameplay-role labels (cat vs mouse vs rocket).

## Object hierarchies (done, tools/dc_objects.py)
`NJS_CNK_OBJECT` (52 bytes: evalflags, model*, pos, ang (BAMS), scl, child*, sibling*) trees are located by linking to the known models; 4,595 candidate nodes, 80 roots, 60 assembled multi-part objects exported to `assets/dreamcast/objects/obj_<offset>.obj` (contact sheet `local/objects_sheet.png`). Identified: cat (157 vertices, root 0x778c4), big-eared mouse in 8 variants (96 vertices), a second mouse-like body (0x7e138, 0x860ec), two round characters with 74/77 vertices (second set with wings/halo), six rockets (113 vertices), board pieces. Remaining: texture-id to PVR mapping, morph animation playback, exact role labels.

## Textures and rendering (2026-11-12, verified visually)
- Every `ENGLISH/*.PRS` is a PRS-compressed PVM texture archive (`tools/prs.py`; 54 archives, 978 named PVRs): one per UI screen (TITLE, MENU, PUZZLE, BATTLE...), plus CAT (4), MOUSE (10), CHAO (9), BIGCHAO (4), BATTLEMODELS (38), EFFECT (56), ROCKET_EF (12). They decode with `tools/pvr2png.py` (954 of 978; 24 use a format not yet handled). Output file names are `<archive>_<texname>.png`.
- Texture-name lists (`NJS_TEXNAME` arrays: name pointer, attr, 0) are baked into `1ST_READ.BIN` for every screen and model (55 found; cat: c_cat01-04 at 0x75c68, mice: c_mouse01-10, chao, chu_p, vw...). Strip chunks carry the index in the texture id (`id & 0x1fff`).
- `tools/dc_objects.py` now exports UVs and per-triangle materials (`obj_<off>.obj/.mtl`, `texN.png` = index N of the model's list). `tools/dc_render.py` is a small software renderer: the assembled cat (root 0x778c4) with c_cat01-04 renders correctly (orange body, spiral eyes, zigzag teeth).
- Animation: the 8 near-identical mouse/chao objects (96/74/77 vertices) are consecutive keyframe meshes, and the cat head has a 24-frame vertex-morph table (frame pointers at 0x7ceb8). Timing and the state-to-animation mapping still need to be read from the code (SH-4 disassembly); not done.

## Animation data (2026-11-13)
- Frame lists are arrays of object pointers: at file offset 0xa37b0 a 24-entry array (8 mouse walk keyframe objects 0x7efb8..0x85538, then 16 chao/other keyframes 0x8c818..0x98304); other short arrays at 0x75994 (4-frame groups: 0x987b8.., 0xa2640 x4, 0x7e138 x4, 0x778c4 x4) and 0xa3798. The cat head is a vertex-morph table of 24 frames (`tools/dc_anim_scan.py`, table at 0x7ceb4, stride 0x33c).
- Phase driver (Android `FUN_00028ffc`, same code base): the cat's walk phase advances 0.45 per tick and wraps at 20.0; the turn angle uses 16-bit angles with `diffAngle`/`adjustAngle` smoothing. Mapping of the phase to the Dreamcast keyframe index (and per-state animations: rocket-in, hole fall, eaten) still has to be read from the SH-4 code.

## Dreamcast character model selection

- The cat draw dispatcher at `0x8c0119fe` selects texture list `0x8c085c98` and submits model root `0x8c0878c4` for costume modes 0–2. Texture indices 0–3 resolve to `c_cat01` through `c_cat04`. The call to `0x8c0e673e` receives both 24-frame motion descriptors, `0x8c088108` and `0x8c08cfd4`, with the caller's floating-point phase intact. A live renderer needs both tracks.
- Costume mode 3 binds the loaded sprite texture list at `0x8c0b4c24` and submits a quad. Frame `4 + ((int(phase) >> 1) & 3)` uses one of the four cat images. Heading bit 15 selects draw parameter 48 or 52. Tested mode 4 issues no texture or draw command.
- Mouse model preparation at `0x8c01a060` selects one of three eight-object sets for costume modes 0–2 and skips mesh preparation for mode 3. The first set uses `MOUSE` textures in the executable's slot order: 01, 02, 03, **05, 04**, 06, 07, 08, 09, 10. Alphabetical sorting swaps two materials.
- `tools/oracle/dc_character_draw.py` executes the original SH-4 dispatchers, recording texture, morph and quad submissions for 100 cat fixtures and all 24 mouse model preparations. The cat probe supplies the game mode and tutorial predicate. The mouse probe supplies the costume selection. GPU rasterization, animation timing for live callbacks and field occlusion remain open. Next, trace the mouse frame selection and the cat's motion sampling before integrating the models.
- Mouse draw dispatcher `0x8c019e26` uses the supplied integer frame directly for the basic mouse's eight prepared models. Modes 0 and 1 dispatch types 1 and 2 through separate motion and shape routines. Mode 2 uses its prepared models for all three gameplay types. Mode 3 uses sprite frames 0–3 via `frame >> 1`, with the heading split at bit 15. The default type-2 branch submits two shape-texture substitutions around the shape draw. The helper receives the texture list in its third argument. The probe checks 256 costume, type, frame and heading cases at the submission boundary. The upstream phase accumulator, renderer internals and actual occlusion remain open.
- The task draw wrapper at `0x8c01946c` reads the model frame from task offset `0x34`, the mouse type from `0x08`, the heading from `0x20` and the transform position from `0x14`. The probe checks all eight frame values. Two other draw callers calculate frames directly: `0x8c051a76` uses `(age / 4) & 7` and `0x8c05144c` uses `(age * rate / 8) & 7`, where age is at `0x04` and the byte rate is at `0x2d`. The probe crosses the wrap boundaries for both callers and includes rate zero. These are draw-time calculations from supplied snapshots. Next, trace the gameplay task updates that write `0x34` and their pause and reset behavior.
- The gameplay writer at `0x8c019b0c` stores the low three bits of the shared clock `0x8c1ae8d8`. The stage setup calls the clock reset at `0x8c018698`. The loop runs the task pass before incrementing the clock. A collision branch at `0x8c019a00` can turn the mouse and bypass the write, preserving its last pose. The source probe verifies wrap and reset on two tasks, the collision bypass, and the loop's hold paths with controlled return values from the run-state callbacks. Next, verify which user actions drive those callbacks and how the cat animation phase relates to the same clock.
- The scheduler probe now executes the original device and run-flag gates. The device latch at `0x8c1ae8b0` is set by errors -33/-23 or by polled statuses 6/7/9 outside device mode 4. It remains set until the reset routine clears it. A clear latch permits updates and services device statuses 0 and 6. The separate run flag at `0x8c0859e4` also gates the task pass. The probe still supplies the transition callback's return and the device status inputs. Controller pause, the transition state machine, and cat motion remain open.

## Live 3D drawing (2026-11-17, first step)
`tools/export_dc_models.py <assets/dreamcast>` packs the cat (object 0x778c4, textures CAT c_cat01-04) and the basic mouse's eight walk keyframes (objects 0x7efb8 ... 0x85538, MOUSE textures in the executable's slot order) with their textures into `dreamcast/models.bin`. `game/app/model3d.hpp` loads it and draws a model with `SDL_RenderGeometry` (CPU transform with yaw/pitch, flat shading, triangles sorted back to front and submitted in texture runs; works with the software and the accelerated renderer). `ccr <assets> models` shows the cat and the mouse's 8-frame walk cycle live (checked by screenshots at several yaws: geometry and textures match `tools/dc_render.py`). **Open for full support:** the other models and their texture lists (chao/special characters, rockets, board pieces in BATTLEMODELS: floors yuka*, walls kabetx*, windows mado, rocket lids rokefuta*), the cat's 24-frame head morph, per-state animations (turn, rocket-in, hole fall, eaten), the camera and lighting the game uses, depth ordering vs the original, and drawing these in Puzzle/Battle instead of the mobile sprites (a setting).

**BATTLEMODELS texture list and rocket models identified (2026-11-17).** The `NJS_TEXNAME` array at 0x75a8c in `1ST_READ.BIN` lists, in this order (material index = position): sphere_tx, ins, bluemado, itablue, itaorange, orangemado, itared, redmado, greenmado, itagreen, outs, rue729, rokefuta01-04, newk1, newk1s ... newk4s, s01, rfire01, rfire04, rfire03, rfire02, yuka01-06, kabetx01-03 (the first array slot holds a stray "Dreamcast Gun" string and is not a texture). Evidence for the order: the four 113-vertex rocket objects 0x9a340 / 0x9b490 / 0x9c5e0 / 0x9d730 use the ita/mado pair of one colour each (blue, orange, red, green) and render with those colours; the four 21-vertex objects 0x987b8, 0x98b20, 0x98e88, 0x991f0 use materials 12-15 = rokefuta01-04 (rocket lids); 0xa0258 uses 25 (rfire01, exhaust), 0xa2114 uses 35 (kabetx01, wall). Exported in `models.bin` as rocket_blue/orange/red/green, lid1-4, fire, wall and shown by `ccr <assets> models`. Still unassigned: floor tiles (yuka*), the other wall and window pieces, the two-colour rocket variants (0x9e8bc, 0x9fa48), newk* (likely the player marker/cursor models) and s01/ins/outs.

**Cat head morph exported and played (2026-11-17).** The 24-entry table at 0x7ceb4 in `1ST_READ.BIN` holds {index, pointer} pairs; each pointer addresses 69 xyz float triples (828 bytes) in the head model's vertex order, in the model's own space (the head sits in object space as a pure translation, checked for all 69 vertices). Frames 0-7 and 8-15 are the same eight poses repeated and 16-23 a third set; frames 17 and 23 equal the base pose. `tools/export_dc_models.py` writes these as 24 full pose arrays on the cat model (`CCM2` format) and `model3d.hpp` draws a chosen frame; `ccr <assets> models` plays them (screenshots show the zigzag teeth, the yellow spiral eyes and different mouth/head shapes across frames). Which frame is shown when (the game's state-to-frame mapping and speed, the two motion descriptors 0x8c088108 / 0x8c08cfd4, and how the eight mouse keyframes are sequenced per state) is not yet taken from the draw code.

**3D characters in live play (2026-11-17, first integration, behind a setting).** `models_3d = true` in `settings.ini` (Options > Settings row "3D characters", or `CCR_MODELS=1`) makes the field draw cats and mice as the Dreamcast models from `dreamcast/models.bin` instead of the sprites. Mouse: frame `gtime & 7` of the eight keyframes (the game's rule: `0x8c019b0c` stores the low three bits of the shared clock, `0x8c019e26` draws that frame directly). Cat: the base head pose (frame 17) only, because the game's morph-frame rule is not decoded. Heading: the entity's turn angle (`heading << 14`, smoothed by the ported angle logic) turns the model about the vertical axis. **Provisional, not verified against the original:** camera pitch (50 degrees), model scale, anchor point, lighting (flat shade) and the yaw offset (180 degrees minus the angle); the rocket entry, hole fall, spawn and eaten animations and the golden/special mice still use sprites. Checked headlessly by screenshots in Puzzle (stage 21, mice walking east, cats in several headings) and Battle.
