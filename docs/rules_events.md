# Rules spec: battle roulette events (draft, iOS 1.1.2 `CCR`, ARM Thumb-2)

Evidence: annotated disassembly (`analysis/asm/ios_events.asm`, made with `tools/ExportAsm.java`). Event handlers run once per
game frame; counters below are frames. Frame rate is not yet measured (60 fps assumed, to be confirmed from the main loop).

| Event (internal name) | Effect set on start | Duration | Notes |
|---|---|---|---|
| Speed Down (`RL_Eve_SpeedDown`/`Dest`) | `GA_SetCharaSpeed(0.3)` | 0x1E0 = 480 frames | on end speed returns to 1.0 (`RL_Eve_SpeedDownDest`) |
| Speed Up (`RL_Eve_SpeedUp`/`Dest`) | `GA_SetCharaSpeed(2.0)`, `GE_SetProhibitGenerator(4)` | 480 frames | generators un-blocked (`SetProhibitGenerator(0)`) at frame 0x12C = 300; speed back to 1.0 at the end |
| Mouse Mania / "Chu2 Fever" (`RL_Eve_Chu2Fever`) | `TI timer 2`, `GE_SetProhibitGenerator(0xC)`, `GE_SetChu2Fever()` | 0x258 = 600 frames | `GE_CancelChu2Fever` on end |
| Cat Mania / "Neko Fever" (`RL_Eve_NekoFever`) | `TI timer 3`, `GE_SetProhibitGenerator(0xF)`, `GE_SetCatFever()` | 0x258 = 600 frames, scaled in some game types by a table value (multiplier 2.0 seen) | a cat sound plays every 16 frames with ~30% chance (random < 0.3) |
| Mouse Monopoly (`RL_Eve_Hitorijime`) | not yet read | not yet read | `MO_StartHitorijime` / `MO_StopHitorijime` |
| Cat Attack (`RL_Eve_NekoPresent`) | not yet read | not yet read | cat intro animation `RL_Eve_NekoPreEnsyutsu*` |
| Everybody Move (`RL_Eve_Hikkoshi`) | not yet read | not yet read | rockets move; `RO_ShuffleRockets` |
| Place Arrows Again (`RL_Eve_Replace`) | not yet read | not yet read | |

Outcome index -> event mapping and the roulette weights are in `docs/roulette.md` (index 5 calls `RO_GetNetShuffleRocketsAssign`,
i.e. the rocket shuffle). The index order of the other seven still has to be read from the `RL_RouletteExec` switch table.

## Version audit (iOS)
Event, timer, generator and game-state functions (40 compared: `RL_Eve_*`, `GA_*`, `TI_*`, `GE_*`) have identical compare/move
immediates and float constants in iOS 1.0.2, HD 1.0 and 1.1.2. The only flagged difference is `GE_Generator4Exe` in HD 1.0
(identical constant set, different order or count: needs a closer look). Android and the Dreamcast/GBA code are not yet compared.

## Roulette presentation (what the player sees; not yet in the app, 2026-11-13)
In the original a pink "?" mouse entering a rocket starts the roulette: `RL_RollRoulette4` creates a roulette task that flies in over the rocket (30 ticks), spins (90 ticks), then the event task starts at tick 121 (the app's simulation does all of this; only the picture is missing). The wheel is drawn by `RL_RouletteDraw2D` / `RL_RouletteDrawPriority` -> `Render::drawRoulette(x, y, z, angle)` at the rocket's position, rotating with the task's angle field (+0x20 * constants), as a **3D object** (`set3DView`, textures from the battle texture space; the Dreamcast has `BATTLEMODELS_sphere_tx` and `EFFECT_*`/`GAMEVOICE_*` banks). The event announcement art/voice, the cat pre-show of "Cat Mania" (`RL_Eve_NekoPreEnsyutsuDraw2D/3D`) and the per-event effects are separate draw callbacks. None of this is drawn in the app yet, so a roulette currently shows only its effect (music change, sound 10, behaviour), which is a gap.

## GBA roulette event dispatcher (ROM `0x08007840..0x08007B90`, found 2026-11-13)
Event handler with a per-event countdown byte (`+0x1a`, 0x3c = 60 frames at the start) and the event index byte (`+0x19`). Two Thumb jump tables: the **start-of-event** table (index <= 7: 8 entries; entries for outcomes 4, 5 and 6 all jump to the common exit, i.e. no start sound/effect, the others play sound ids 0x52/0x46/0x51/0x45/0x4f/0x50/0x4a) and the **end-of-event/effect** table (`cmp r0, #0xb`, so indices 0..11: **12 distinct handlers** at 0x0800796C, 0x080079B4, 0x080079D0, 0x080079E4, 0x080079F8, 0x08007A60, 0x08007ADC, 0x08007AF8, 0x08007B34, 0x08007B44, 0x08007B6C, 0x08007B88). So the GBA battle roulette has **12 outcome handlers**, 4 more than the Dreamcast/mobile 8: this contradicts the "13 events (5 new)" of the research document (five named new events); one of its five may be a variant of another (e.g. Mouse Mania (Special!) sharing a handler) or the 13th is handled outside this dispatcher. Not yet decoded: which index is which event, their durations and effects, and the GBA roulette weight table.

## Roulette and input (2026-11-13)
Android: the battle loop (0x4a9a8 and the net-battle loop at 0x53588) calls `Core::isRouletteActive()` each frame and, while it is true, `Input::invalidateArrow(player)`; `FourBattleLoop` and the timer still run, so the game does not freeze, human arrow placement is dropped. Not yet traced: whether characters keep moving during the spin (nothing in the loop pauses them), and the Dreamcast and GBA behaviour. The port drops human placement while `BattleGame::rollPending()`; CPU placement is unaffected (it does not go through this input path in the original).

CPU players during the roulette (Android, read 2026-11-13): `Core::isRouletteActive` has six callers: the human input loops of the battle screens at 0x4a83c, 0x53588, 0x60a3c, 0x610bc and 0x66c78 (two of them belong to other game modes) and `drawArrowInfo` (0x6d05c, hides the arrow info while the wheel spins). The CPU think task (`FUN_00029fa8`) does not call it, so CPU arrows are not blocked by the roulette; the port matches (CPU placement does not go through the human input path). Gaps: the port has no `drawArrowInfo` counterpart; Dreamcast, GBA and iOS not checked.

Audit tooling (2026-11-13): `tools/callgraph.py <decomp .c> <function> [depth]` prints a function's static callee tree. It shows the limit of the approach: `FourBattleLoop` only calls the collision loop and task servers, because the game objects (cats, mice, arrows, rockets, roulette, CPU, HUD) run as scheduled tasks reached through function pointers (`SmpTskChangeExeFunction`/`ChangeDrawFunction`, `Render::addRendernodeCustom`). The complete "what does the battle screen do each frame" list therefore has to be built from the task-creation calls (`SmpTsk*` creators and the `*Init` functions the battle start-up calls), not from the static call tree. Not done yet.

## Cursor lock vs roulette (2026-11-13)
`CU_SetCursorLock` has three callers: `PuzzleStageInit`, and `FUN_0003c9f0` (the roulette event start that also calls `GE_SetProhibitGenerator(0xf)` and `GA_SetCharaSpeed`, i.e. the Everybody Move / Cat Attack events; the port's `cursorLock` for events 5 and 6 mirrors it); `CU_SetCursorUnlock` is called from `FUN_0003c8b0`/`FUN_0003c8d4` and the battle start. `CU_CursorControlByParameter` (what the CPU task calls to move its cursor) fails while the lock is set. So in the Android code the spin itself does not lock the CPU cursors; only the human input is gated. Not proven that no other route stops the CPU during the spin (task scheduling was not traced).

## Four-battle phase machine (`FourBattleLoop` 0x31918, jump table of 6 phases; Ghidra could not recover the table, read from the binary 2026-11-13, `tools/thumbdis.py`)
Phase entry points: 0 = 0x31ac0 (set up: deformer flag, game flag on, `SmpTskInit/EntryAll`, `RankCrawnInit`, speed, BCD and game timers, `SC_InitScoreBoard`, `FI_InitFieldCollision`, `RO_StartRocket4Manager`, `CU_StartCursor4Manager`, a sound, CPU select types, `BGM_Play`), 1 = 0x31b72 (`CU_SetCursorUnlock`, `AR_StartArrow4Manager`, `GE_StartGenerator4Manager`, `RL_StartRoulette4Manager`), 2 = 0x3193a (running; below), 3 = 0x31bb4 (`BGM_Change`, HUD render node), 4 = 0x319f2 and 5 = 0x31a58 (end of round/results, not read yet). In phase 2, only while `RL_GetRoulette4Status() == 0` the game timer counts up and the BCD timer counts down; at remaining times 5, 4, 3, 2, 1 and 0 seconds (BCD 0x500 .. 0x000, seconds in bits 8..11) `ChuSECall(0x13 - seconds)` plays a tick sound (ids 0x0e..0x13), and banners are started with `BattleCountInit`: at 0x300 mode 2, at 0x200 mode 1, at 0x100 mode 0, and at the three marks 0x10000 (0x80<<9), 0x20000 (0x80<<10) and 0x3000 (0xc0<<6) the modes 4 (sound 0x7e), 5 (sound 0x7d) and 3 (sound 0x7f plus `BGM_Change(6, 0x3c)`); at 0 the game flag is cleared, pause disabled and the result task entered. Mapping of those larger marks to minutes is unverified (the BCD layout puts minutes at bits 16..19, so 0x10000 and 0x20000 are 1 and 2 minutes left, 0x3000 is 30 s left). The port does not play the five tick sounds yet.

Implemented 2026-11-13 from the phase-2 reading above: the round countdown (`BattleGame::clock`) stops while the roulette wheel task is alive (the port's `roll_.active`; `RL_RollRoulette4` sets the status to 1 when it creates the wheel task), so a spin lengthens the round by its duration; and `ChuSECall(0x13 - seconds)` plays when 5, 4, 3, 2, 1 and 0 s are left (the BCD value is mm:ss:ff with ff = frames, so each mark is hit once). The determinism, full-battle, CPU and netplay tests still pass (0 differences / 0 desyncs). Both are Android-derived; whether the other versions pause the timer for the roulette is unchecked. Still unported from the same function: the minute/30 s banner marks (`BattleCountInit` modes and sounds 0x7d-0x7f) and the round-end result phases 4 and 5.

### Phases 4 and 5 (end of round), first reading (2026-11-13, `tools/thumbdis.py` 0x319f2..0x31ac0)
Phase 4 (0x319f2, game type 0 = battle): calls `FUN_00031890` each frame and, once a counter at +0x...c5a exceeds 0xf0 (240 ticks = 4 s after the end), waits for an input flag (`getFlag(1)`, cleared when seen); it then counts how many of the four player records (+0x10..+0x1c of a table) are zero, and if exactly one is (a single winner) goes to the result/winner path at 0x31eda, otherwise resets a counter and keeps going (tie/other handling not read). Phase 5 (0x31a58) is a sub-state machine on a counter at +8 (0..3): sub-state 3 counts frames, waits for input flag 2 or about 1,340 frames (0xa7 << 3), and plays `ChuSECall(0x15)` every 32 frames while the counter is below 0x60 and at 0xf0 starts the next step (0x31f50); states 0..2 lead to the winner announcement tasks (0x31cf0, 0x31d28, 0x31d72) with `FUN_000318ac` (the HUD render node). These are the result screen's timings; they need the result art and HUD before they can be ported and checked. Not ported.

## Roulette events read and ported 2026-11-14 (iOS 1.1.2 `RL_Eve_*`, same structure in Android `FUN_0003c9f0`)
Outcome -> task (from the `tbb` switch in `RL_RouletteExec`, iOS 0x1cd32): 0 NekoFever, 1 Chu2Fever, 2 SpeedUp, 3 SpeedDown, 4 Replace, 5 **Hikkoshi** (Everybody Move), 6 **NekoPresent** (Cat Attack), 7 **Hitorijime** (Mouse Monopoly).
- **Hikkoshi**: state 0: `ChuSECall(0xc)`, `GE_SetProhibitGenerator(0xf)`, `RO_ShuffleRockets()`, `CU_SetCursorLock`, `GA_SetCharaSpeed` (0); state 1: ends when its counter exceeds 0x3b (60 ticks); `RL_Eve_HikkoshiDest`: prohibit 0, cursor unlock, speed restored. `RO_ShuffleRockets` (local path): permutation chosen by `TI_GetGameTime()`: free-for-all `ffa[(t & 0x3f) mod 9]`, team `team[(t & 0xf) mod 5]` (tables read from the binary: ffa {1,0,3,2} {3,0,1,2} {2,0,3,1} {1,3,0,2} {2,3,0,1} {3,2,0,1} {1,2,3,0} {2,3,1,0} {3,2,1,0}; team {1,0,3,2} {2,0,3,1} {1,3,0,2} {3,2,0,1} {2,3,1,0}); rocket i takes the cell of old rocket perm[i] (`FI_ChangeFieldCollisionID`) and the position table is permuted likewise; the rockets slide visually for 60 ticks but the owner change is immediate. The global mode 0x10 branch (net battle, owner list by rank) is not ported.
- **NekoPresent**: state 0 as above (lock, prohibit 0xf, speed 0, present tasks at each opponent rocket); at counter > 0x3b: `ChuSECall(7)`, for each player p with `RL_ENP_CheckNekoire(roller, p)` (p != roller; in team mode also a different parity) `SC_CatHasCome(p)` (in team mode only p < 2), then the task ends (`RL_Eve_NekoPresentDest`). `MO_CatHasCome` and `CU_CatHasCome` are empty functions. The old port had this event end after one tick and no score effect.
- **Hitorijime**: `MO_StartHitorijime(roller)` sets a global (iOS 0x29a260) read by `MO_MouseExe`/`MO_MouseJimeExe`, `GE_SetProhibitGenerator(4)`, `GE_SetChu2Fever()`; ends when its counter exceeds 0xef (240 ticks): prohibit 0, `GE_CancelChu2Fever`, `MO_StopHitorijime` (-1). Not ported yet (the mouse behaviour `MO_MouseJimeExe` is read: below).
Implemented in `BattleGame` (`shuffleRockets`, `nekoCheck`, `teamMode`); `game/tests/events_test.cpp` checks over 12 stages x 2 modes x 6 seeds (626 shuffles, 149 attacks) that rocket owners stay a permutation and positions follow; the whole-battle goldens (26/26), roulette selector, score, determinism and CPU tests are unchanged. NOT yet diff-tested against the original code for these two events.

## Whole-battle diff with the roulette events (2026-11-14; `battle_full_test` with FULL=1, goldens from `tools/oracle/make_battle_golden_gt.py`)
The emulated original (Android, 26 recorded battles x 3000 frames, scripted arrows) is run with a chosen roulette threshold table (all 128 entries = one value: outcomes 0..7 selectable), BCD time and game time; the port runs the same battles with `rouletteEnabled`, the same fixed values and compares the frame of every score change. Fixes this found:
- The harness itself kept the roulette globals of the previous battle (a roll still running at frame 3000 blocked every later case); `make_battle_golden_gt.py` clears them per case.
- **A new roll deletes the running event task** (`RL_RollRoulette4` deletes the task stored in its global): the original calls `GA_SetCharaSpeed(1.0)` (the Dest function) in the roll frame (logged). The port ran events side by side before; it now runs `eventDest` for the running events at a new roll (`cancelEvents`).
- Speed changes made by an event task take effect at the task's pool slot inside the frame: entities after the event slot already move at the new speed in that frame (logged: at the end of a Speed Up, 12 of 27 mice ran before the `GA_SetCharaSpeed(1.0)` call; at the start all mice had run, so the start takes effect next frame). Implemented as `Sim::spdSlot` (entities are then processed in slot order for that frame). The port's slot accounting is one slot off in some frames (one mouse on the wrong side of the event slot), so a few battles still differ by 1-3 frames.
Results: outcome 0 (Cat Mania, threshold 0): 26/26 identical; Speed Up (bcd 0, threshold 0.7): 21/26 (the 5 that roll differ by 1-2 frames after the speed change); constant speeds 2.0 and 0.3 without events: 26/26 identical; Cat Attack / Everybody Move / Mouse Monopoly (threshold 0.99 etc.): not matching yet (large differences), to be investigated next. The mouse positions of the original per frame are logged by `tools/oracle/mouse_pos_log.py` for localisation.

Update (2026-11-14, later): `mouse_pos_log.py` now logs the roulette outcome global (0x184c94). At threshold 0.985 and 0.995 (bcd 0) the original picks outcome **7** for the first roll of case 2, the same as the port, so the 0/5 result of the "Cat Attack" diff was really a **Mouse Monopoly** diff (outcome 7), which diverges: the Monopoly port is not matching the original yet. A valid Cat Attack (6) run needs a per-rank threshold (the rows differ by rank); not done. Everybody Move (5, threshold 0.95): the rocket permutation matches the original in the traced case but the battles diverge a few frames later; cause not found.
