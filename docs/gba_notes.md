# GBA version: emulation harness and first results (2026-11-13)

Tools: `tools/oracle/gba_oracle.py` (mini GBA on Unicorn ARM7: memory map incl. IWRAM mirror, IO register file with write-1-to-clear IF, immediate and VBlank-timed DMA, BIOS SWI HLE (Halt/IntrWait/VBlankIntrWait, Div, CpuSet/FastSet, LZ77, RLE, ArcTan, Sqrt), Macronix-ID 64 KB Flash command state machine, keypad, VBlank IRQ), `gba_render.py` (debug renderer: mode 0 text BGs + sprites), `gba_session.py` (cached menu snapshots + key scripts).
The user's ROM boots to the language screen, Sonic Team splash, title (with the title battle demo), Mode Select (Help, 4P Battle, Team Battle, Stage Challenge, Puzzle 1P, Let's create a stage / character, Exchange data, Options) and the puzzle stage select / planning screens. Save type FLASH_V121 (64 KB).
Key map used: A=1 B=2 Select=4 Start=8 Right=16 Left=32 Up=64 Down=128 R=256 L=512 (R starts the run in the puzzle planning screen: "R Button: Start / Dash"). The puzzle cursor is a pointer sprite moving 2 px per frame; the selection box sprite snaps to the 16-px cell grid (board origin x=40, y=2).

Findings
- Logic rate is 60 Hz; a mouse moves **1.6 px per frame = 1.5 world units per tick** (cell 16 px = 15 units): identical speed to Android/iOS. Sprite position = p0 - floor(1.6 k) (sub-pixel accumulation), measured on one mouse over 60 frames.
- **Puzzle stage 1 ("Where to go?") with one arrow placed at cell (6,4) pointing up: the GBA run removes 30 mice at frames 62, 72, ..., 822 (30 events across 820 frames); the C++ simulation with the same arrow predicts 61, 71, ..., 821 - identical sequence, constant +1 frame (the sprite disappears one frame after the logic removes the mouse).** This exercises serpentine walls, edge wrap, arrow turns and rocket entry.
- Not yet done: automating arrow placement for more stages (needs the panel order per stage), cat/hole cases, battle mode (GBA has 4P/team battle with CPUs and a roulette: "Night Time!" event seen in the title demo), speeds in battle options, fixed-point details. The harness runs the real game so these are now measurable.

## GBA arrow placement and CPU code located (2026-11-13)
Found by comparison, no emulator beyond the Unicorn harness: placing an arrow with the A button in Stage Challenge (a 1P mode that runs in the harness; 4P/Team Battle need a link cable and stop at a cable error) and diffing which code writes RAM in that frame against a frame without input gave the arrow primitive **`0x08004EF0`** (Thumb; r0 = player/cursor record with the player id at +3, x halfword at +8, y halfword at +0xc; r1 = direction). It allocates the arrow object (exec function 0x08005045, life counter 0x258 = **600 ticks**, the same arrow life as the other versions), keeps a ring of **3 arrows per player** (when the third is placed the oldest is shifted out), and writes `0x60 | player | direction` into the field map. In the title demo the CPU players reach it from exactly one place: **`0x08009844`**, a wrapper that reads the CPU's chosen target from a 16-byte per-player record at `0x03000220 + 16*player` (x at +0xc, y at +0xd, direction at +0xe), checks that the target cell is empty with `0x08009464` (field map at 0x030029A0, 27 bytes per row, cell (x, y) at lattice (2x+1, 2y+1), empty = high nibble zero) and then calls 0x08004EF0. The CPU decision code is the block **0x08009000-0x0800A5FF** (about 3% of executed instructions each for 0x0800A4C0 and 0x08009280): `0x080094A0` is a heat-map scan that keeps the two best cells (value halfword at 0x03000500/0x03000502, cell at 0x03000504-0x03000507) over a table of 3-halfword entries at 0x0300028E; `0x08009568` dispatches on the low 2 bits of the byte at 0x03000274 to `0x080091C4`/`0x080094A0` with the tables at 0x03000350 and 0x03000428. The structure matches the task-pool/heat-map design of the other versions. Not yet read: the per-player think state machine (0x080095D8 onward, 0x0800990C, 0x08009A20, 0x0800A4C0), how the heat map is built, the delay/timing, and the random source (the LCG at 0x080054F4 is not called by this code in the demo, so difficulty variation may come from elsewhere). Disassembly of the block: `local/gba_ai.txt` (derived, not committed).

### GBA CPU: what the first read of 0x0800912C-0x08009810 shows (2026-11-13, from the disassembly; not yet diff-tested)
- **Init (`0x080096F8`)**: copies a 16-byte default record from `0x080A94A4` to `0x03000220 + 16*player`, calls the personality step, sets the cursor cell to ((x_px - 2) >> 1, (y_px - 2) >> 1) of the player's record (halfwords at +8 and +0xC), zeroes the phase byte `0x03000274`, clears the three heat tables (`0x0800912C`: 9 rows x 12 cells of halfwords at 0x03000278, 0x03000350, 0x03000428) and the best-cell registers (`0x08009188`: halfwords at 0x03000500/0x03000502 and four bytes at 0x03000504-0x03000507).
- **Personality (`0x080096A8`)**: the CPU type is a byte at `0x03002C90 + 3*player`; type 5 means random and draws `(LCG() & 3) + 1` with the ROM LCG (0x080054F4, the same generator as the other versions); the type indexes a byte table at `0x080A94E4` whose value becomes record byte +1 (behaviour flags); if the byte at `0x03002990` is 6 the flag bit 6 is cleared. So the difficulty/personality system is there, and the random source is the shared LCG, used once at start-up (which is why it was not seen in the mid-battle trace).
- **Heat diffusion (`0x080091C4`, r0 = source table, r1 = destination table)**: iterates a rectangle given by a 4-byte record at `0x080A94B4 + (phase & 0xC)` (x0, x1, y0, y1); for each cell it sums, over the four neighbours (wrapping 0..11 and 0..8), the neighbour's source value >> 3 when the wall between the cells is open (wall lattice byte at `0x030029A0`, 27 bytes per row of the doubled lattice, zero) and the neighbour cell is not blocked (`& 0xA0` zero), added to the cell's own source value, and stores the sum in the destination. `0x08009568` calls it with the tables swapped by the phase (`0x03000274 & 3`: 0 -> 0x03002DE0 (a different source), 1 -> 0x03000350 -> 0x03000428, 2 -> 0x03000428 -> 0x03000350, 3 -> 0x03000350 into 0x03000278 and then runs the best-cell scan 0x080094A0): a fixed number of diffusion passes, then a scan.
- **Best-cell scan (`0x080094A0`)**: walks the 0x03000278 table (24-byte rows of 12 halfwords) keeping the best two values among cells that pass the empty-cell test (0x08009464), recording value and cell in 0x03000500-0x03000507.
- **Placement (`0x08009844`)**: if the chosen cell passes the empty-cell test, call the arrow primitive 0x08004EF0 with the direction in record byte +0xE.
- This is the same task-pool/heat-map family as the mobile and Dreamcast CPU (shift-by-3 diffusion, best cell, direction, place). Remaining to read: how the source heat is seeded (cats/mice/rockets/holes), the direction choice (record +0xE), the timing/delay between actions, the per-phase driver (0x0800990C, 0x08009A20 ... 0x0800A5FF), then a differential test of each pure function (0x080091C4, 0x080094A0, 0x08009464) against the port with random states in the harness, as done for the other versions.

### GBA CPU: more of the block (2026-11-13, first read, untested)
- `0x08009748` returns 1 when the CPU cursor's cell ((x_px - 2) >> 1, (y_px - 2) >> 1 from the record's halfwords +8/+0xC) equals the target cell at record +0xC/+0xD. `0x0800977C` moves the cursor sprite position (bytes +0x1E/+0x1F, pixels) **2 px per call toward the target cell centre (cell*16 + 8)**, the same 2 px per frame as the human cursor; `0x080097D0` then writes the sprite coordinates (+0x29 and +3 offsets) and the facing; `0x08009810` = at-target check, move, redraw, at-target check (returns 1 when arrived). So the CPU cursor travels like a human's.
- `0x0800990C` (args: player, two coordinates, direction index) and `0x08009A20` (args: two coordinates; **draws a second random number `LCG() & 3`**, then tries the four directions starting from that one in order, using the direction offset table at `0x080A94FC`) are wall-aware cell walkers over the field map (`0x030029A0`, cell blocked when `& 0xA0`, wall flags `& 0x80`): they decide which direction an arrow on a cell should take or whether a cell is a valid arrow position. Both are pure functions of the field map and so are testable like the others.
- So the GBA CPU uses the LCG at least twice: personality at start (type 5 = random) and a random starting direction in the 0x08009A20 search. Everything else read so far is deterministic.
Next step unchanged: finish reading 0x08009A20-0x0800A5FF (the per-player state machine and the seeding of the heat), then differential tests of 0x080091C4, 0x080094A0, 0x08009464, 0x0800990C, 0x08009A20 in the harness.

### GBA CPU: direction choice and wall counting (2026-11-13, first read, untested)
- `0x08009B2C` (args: cell x, y; returns direction << 2): for each of the four directions (offset table at `0x080A950C`) it steps along the wall-aware field with `0x080090FC` (one cell step that stops at a wall) up to 3 cells and counts the free steps; it returns the direction with the **longest free run**, and **a tie is broken by a coin flip, `LCG() & 1`** (third random use: tied runs keep the first with probability 1/2 each time).
- `0x08009C80` (args: x, y) counts the walls around a cell on the doubled lattice (four neighbours at lattice offsets, reading the wall bytes of `0x030029A0`) and records which side has one (8 / 4 / ...), a "dead end / corridor" classifier used to pick the arrow direction when walls decide it.
- `0x08009D60`, `0x0800A434` and `0x0800A654` are the remaining large functions of the block (per-player think/seeding); not read yet.
RNG uses found so far in the GBA CPU: personality at start-up, the starting direction in 0x08009A20, the tie-break in 0x08009B2C.

### GBA CPU: the per-player decision function `0x08009D60` (2026-11-13, structure only)
Reads the player's cursor cell (bytes at `0x03002C68 + 2*player`, (px - 2) >> 1), then for each of the four neighbour cells (offsets from a table at `0x080A9523`) loads that cell's heat from the table at `0x03000278` (off-board neighbours get the constant -50 (0xFFCE), +0x2E more when personality flag bit 1 is set), **bubble-sorts the four directions by heat, descending**, then walks them in that order checking the wall lattice (`0x030029A0`) on both sides of the neighbour cell and, when a wall configuration qualifies, builds a candidate arrow record (cell, direction from the table at `0x080A951C`) and queues it with `0x08009870` (a queue of up to 3 records at `0x03000268`, count at `0x03000260`). The queue is what the placement wrapper `0x08009844` and the cursor mover consume. Remaining: the rest of this function (0x0800A000-0x0800A434), the heat seeding in `0x0800A434` and `0x0800A654`, and the phase driver tying them to `0x03000274`.

### GBA CPU: the area search `0x0800A434` (2026-11-13, structure only)
Gated by `0x08009D44` (a readiness test, not read yet). The threshold starts at 3, or 0 when personality flag bit 3 is set. It scans the **diamond of cells within Manhattan distance 6 of the cursor** (rows -6..6, columns -(6 - |dy|)..(6 - |dy|)); for each cell inside the board that passes the empty-cell test (`0x08009464`) it takes the cell's heat (`0x03000278` table) **shifted right by a distance-dependent amount from the byte table at `0x080A955C` indexed by |dx| + |dy|**, keeps it if it beats the running best (and the threshold), derives the arrow direction for that cell from the offset with `0x080098A0`, requires the path check `0x0800990C` to accept it, and finally queues the best candidate (cell, direction) with `0x08009870`. `0x0800A654` (reads record bytes +1 and +2, `-1` at +2 means no target) looks like the sibling that follows an existing target. So the GBA CPU = personality flags + heat map + (neighbour rule `0x08009D60` | area search `0x0800A434` | target follow `0x0800A654`) + queue + cursor travel + placement. Not yet read: `0x08009D44`, `0x080098A0`, `0x080090FC`, `0x08009870` beyond the queue push, the lower half of `0x08009D60`, `0x0800A654`, and the heat seeding and phase driver (`0x080095D8` etc. were the sort and swap helpers, not the driver).

### GBA CPU: helpers and tables (2026-11-13)
- `0x080090FC` wraps a cell (x, y) in place: x < 0 -> +12, x > 11 -> -12, y < 0 -> +9, y > 8 -> -9 (the board wraps).
- `0x08009D44` returns 1 when `(0x03000274 & 3) == player`: the CPUs take turns round-robin, one player per phase step; the byte's bits 2-3 select the board quadrant for the diffusion.
- `0x080098A0(dx, dy)` returns the arrow direction (as dir << 2, values 0, 4, 8, 0xC) pointing along the larger offset component; when |dx| == |dy| it draws `LCG() & 1` to choose between two directions from the pair table at `0x080A94EB` (8 bytes: 08 0C | 00 04 | 04 08 | 00 0C for the four diagonals).
- ROM tables: personality flags (`0x080A94E4`, index = type 0..4 (5 draws a random 1..4)): `00 55 66 48 6A`; diffusion quadrants (`0x080A94B4`, 4-byte records x0, x1, y0, y1 selected by `phase & 0xC`): (0,6,0,4), (6,12,0,4), (0,6,4,9), (6,12,4,9), i.e. the board is diffused one quadrant per phase; neighbour offsets `01 00 00 01 FF 00 00 FF` (dx, dy pairs: +x, +y, -x, -y); distance decay shifts (`0x080A955C`): `00 00 01 02 03 04 05 05 05`; candidate direction codes (`0x080A951C`): `00 04 08 0C`. The default 16-byte record at `0x080A94A4` is all zero.

### GBA CPU: the driver and per-player task (2026-11-13, observed callers in the demo + disassembly of 0x0800AA00-0x0800AE20)
- **Global step `0x0800ADF4`** (once per frame): `0x08009568` (one diffusion step, below), `0x080095D8` (sorts the four players' scores, bubble sort on the halfwords at `0x03002C10 + 20*player` with a parallel rank array at `0x0300050C`; used as the players' standing), then the phase byte `0x03000274` is incremented. With step = phase & 3 and quadrant = (phase >> 2) & 3: step 0 diffuses the **seed table `0x03002DE0` into `0x03000350`**, step 1 `0x03000350` into `0x03000428`, step 2 `0x03000428` into `0x03000350`, step 3 `0x03000350` into the **heat table `0x03000278`** and then runs the best-cell scan; each step only covers one board quadrant (rectangles above), so the whole board is refreshed every 16 frames, four diffusion steps deep (each step adds a neighbour sum >> 3).
- **Per-CPU task `0x0800ACE8`** (record at `0x03000220 + 16*player`, state byte +0): state 0 (thinking): increments the counter at +4, runs the think function `0x0800AC1C`; if it chose an arrow, the counter is cleared and the state becomes 1; otherwise after more than 10 ticks it targets the cursor's own cell and runs the mover once. State 1 (moving): runs the mover `0x08009810`; when it returns 1 the arrow is placed by `0x08009844` and the state returns to 0. After either state the stall timer at +8 is updated against the player's score (`0x03002C10 + 20*player`, compared with the value saved at +6): score lower than before -> +0x78, equal -> +1, higher -> 0.
- **Think `0x0800AC1C`**: clears the queue count (`0x03000260`). If personality flag bit 6 (0x40) is set and the stall timer (+8) exceeds 0x257 (599) it runs a special routine `0x0800A854` and then possibly the area search, bumps a counter (+0xA) and resets the timer to 0x21C (540) or, after three uses, to 0. Otherwise, while fewer than 3 candidates are queued: neighbour rule `0x08009D60` if flags & 3, area search `0x0800A434` if flags & 0xC, target follow `0x0800A654` if flags & 0x30; then `0x0800AA1C` finishes (reads the queue). So the personality byte is a bit mask of which rules the CPU uses: types 0..4 = 0x00, 0x55, 0x66, 0x48, 0x6A (rules: 0x55 = neighbour(1), area(1), follow(1), special; 0x66 = neighbour(2), area(1), follow(2), special; 0x48 = area(2), special; 0x6A = neighbour(2), area(2), follow(2), special; 0 = none; the 2-bit fields act as variants of each rule, not yet decoded).
- Unread: `0x0800AAF4`, `0x0800AA1C`, `0x0800A854`, `0x0800A654`, the lower half of `0x08009D60`, the writer of the seed table `0x03002DE0`, and what the 2-bit variants change.

### GBA CPU: target selection and target-follow search (2026-11-13, structure)
- `0x0800AAF4` picks the **opponent the CPU harasses** and stores it in record byte +2 (0xFF = none). Game mode byte `0x03002990`: modes 1 and 6 (team modes) set it to `(player + 1) & 3`; mode 0 (free-for-all) uses the rank order from the score sort (`0x0300050C`, ranks `0x03000508`) with the CPU-type bytes at `0x03002C90 + 3*player` (0 = human): depending on the CPU's own rank it prefers the player ranked first (or second) **when that player is human and has a score above 0**, otherwise the next ranked human with a positive score, else none.
- `0x0800A654` (target follow, flags & 0x30): ends if there is no target; otherwise it scans a window of **|dx| + |dy| <= 4** around the target player's cursor cell (the cursor cell of player `rec[2]` from `0x03002C68`), starting threshold -60 (0xFFC4), +53 more when flag bit 5 is set; for each in-board empty cell it takes the heat (`0x03000278`) and requires it to exceed the threshold and the distance-shifted threshold, derives the direction with `0x080098A0` and the path check `0x0800990C` and keeps the best, then queues it like the other rules.
Unread now: `0x0800A854` (special rule, flag bit 6), `0x0800AA1C` (queue finish), the lower half of `0x08009D60`, the writer of the seed table `0x03002DE0`.

### GBA CPU: the special rule `0x0800A854` (flag bit 6, used when the stall timer exceeds 599; 2026-11-13)
Collects up to 8 random candidate cells: up to 8 tries of x = (LCG * 3) >> 13 (0..11) and y = (LCG * 9) >> 15 (0..8) (LCG = the 15-bit output), each kept if its heat is nonzero and the cell is empty (`0x08009464`); adds the two best scan cells (`0x03000504/05` if value `0x03000500` > 0, `0x03000506/07` if value `0x03000502` < 0) when they are still empty; then picks one of the collected cells uniformly ((count * LCG) >> 15) and chooses its arrow direction with a coin flip (`LCG & 1`) between the random-start search `0x08009A20` and the wall classifier `0x08009C80`; the result is queued with `0x08009870`. This is the "I have been stuck too long, do something" fallback. It uses the LCG 2 + up to 16 + 1 + 1 times per call.

### GBA CPU: queue finish `0x0800AA1C` (2026-11-13)
Takes the queued candidates in order (`0x03000268`, 4 bytes each: x, y, direction code) and accepts the first one that is not an exact duplicate (same cell **and** same direction) of one of the CPU's own live arrows (count at record `0x03002C10 + 20*player` +6, then entries at +7.. (direction) and +8.. (x, y in pixels, (v - 2) >> 1), 4 bytes each); the accepted candidate is copied into the CPU record's target fields (+0xC x, +0xD y, +0xE direction) and the function returns 1 (so the task goes to state 1, moving). If every candidate is a duplicate it returns 0.

### GBA CPU: the neighbour rule `0x08009D60` in full outline (2026-11-13)
Stage 1 (up to the sort): cursor cell (cx, cy); for each direction k = 0..3 the neighbour cell (cx + dx_k, cy + dy_k) (offsets `0x080A9523`, pairs 01 00 / 00 01 / FF 00 / 00 FF) gets heat `H_k` from `0x03000278`, or the constant -50 (-4 when personality flag bit 1 is set... the code adds 0x2E to 0xFFCE, i.e. -50 + 46 = -4) when off the 12 x 9 board; the four (k, H_k) pairs are bubble-sorted by H descending. Stage 2: for the sorted directions while H_k is below the threshold the second stage compares against (`rec[+?]` threshold `r6` = -50 or -4), the code examines the wall lattice on the far side of the neighbour (offset 2 cells, `0x080A9523` at index k + 2 and k + 1) and, depending on which walls exist, queues an arrow on the **cursor's neighbour** with the direction `0x080A951C[k + 3]` (or on the near cell with `0x080A951C[k + 2 + ((phase >> 2) + player) & 1]`, a pseudo-random alternation by the phase counter, no LCG): the three wall cases are (a) wall ahead of the neighbour: arrow turning away, (b) wall beside: arrow along the wall, (c) open: alternate by phase parity. Stage 3 (reached when fewer than 3 candidates exist and flag bit 1 is set): for each of the four directions it steps up to two cells (offsets `0x080A9531`, diagonal pairs 01 FF / 01 01 / FF 01 / FF FF in the wall-checked field), keeps the direction whose reached cell has the highest heat above the threshold, and queues an arrow there with the direction from `0x080A9548` (4-entry table of cell offsets) and code from `0x080A9558`/`0x080A953F`. I have the structure but not yet every constant of stage 2 and 3; those are the next transcription targets (tables: `0x080A9531`: 01 FF 01 01 FF 01 FF FF 01 FF 01 01 FF 01; `0x080A953F`: 0C 00 04 08 0C 00 04 00; `0x080A951C`: 00 04 08 0C 00 04 08 01).

### GBA CPU: heat seeding `0x08008FDC` (2026-11-13; found as the only writer of the seed table `0x03002DE0` in the demo)
Runs every frame only in game modes 0, 1 and 6 (`0x03002990`; otherwise it returns without running the AI). It zeroes the 9 x 12 halfword seed table, then walks two lists of object ids kept in one array at `0x03001610`: the first `n_a` ids (count byte `0x03001690`) are subtracted **100 (0x64)** from the table cell under the object (cell = ((x_px - 0x28) >> 4, (y_px - 2) >> 4) from the halfwords at +0xA and +0xE of the 36-byte object record in the array at `0x03001740`); the last `n_b` ids (count byte `0x03001694`, entries `0x80 - n_b .. 0x7F`) are **added** the weight `0x080A949C[type]` where type is the object byte +0x1B: weights 1, 50, 25, 25 for types 0..3 (so a normal mouse attracts 1, the golden mouse 50, the other two types 25; the first list, subtracted, is the cats: repel 100). Cells outside the board are skipped. After seeding it calls the global step `0x0800ADF4` (diffusion step, score sort, phase counter). So the heat the CPU follows is: mice attract by their value, cats repel, spread over the board through walls by the shift-by-3 diffusion; arrows, holes and rockets are not part of the seed.

## GBA CPU battle score gap, direction-code experiment (2026-11-14)
Whole-battle smoke test (25 Dreamcast battle stages, 4 CPUs, 3 minutes): GBA CPUs mean total score 170.8, the port's Android/Dreamcast-style CPU 520.8. To see whether the inferred ROM direction-code mapping (0 east, 4 south, 8 west, 12 north) caused it, all 24 assignments of the four codes to the four directions were run: the best gives 270.3, the inferred one 170.8, none comes near 520, so the mapping is not the explanation and the GBA CPU scores less in this (Dreamcast-rule) simulation for another reason (different GBA rules and speeds are not simulated, heat/area search only looks 4-6 cells, fewer arrows land on useful cells...). Cause not established; the mapping stays "inferred" until arrow placements are compared with the ROM's own arrow table in a running ROM battle.
