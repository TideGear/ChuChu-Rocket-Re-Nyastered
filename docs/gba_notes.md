# GBA version: emulation harness and first results (2026-11-13)

Tools: `tools/oracle/gba_oracle.py` (mini GBA on Unicorn ARM7: memory map incl. IWRAM mirror, IO register file with write-1-to-clear IF, immediate and VBlank-timed DMA, BIOS SWI HLE (Halt/IntrWait/VBlankIntrWait, Div, CpuSet/FastSet, LZ77, RLE, ArcTan, Sqrt), Macronix-ID 64 KB Flash command state machine, keypad, VBlank IRQ), `gba_render.py` (debug renderer: mode 0 text BGs + sprites), `gba_session.py` (cached menu snapshots + key scripts).
The user's ROM boots to the language screen, Sonic Team splash, title (with the title battle demo), Mode Select (Help, 4P Battle, Team Battle, Stage Challenge, Puzzle 1P, Let's create a stage / character, Exchange data, Options) and the puzzle stage select / planning screens. Save type FLASH_V121 (64 KB).
Key map used: A=1 B=2 Select=4 Start=8 Right=16 Left=32 Up=64 Down=128 R=256 L=512 (R starts the run in the puzzle planning screen: "R Button: Start / Dash"). The puzzle cursor is a pointer sprite moving 2 px per frame; the selection box sprite snaps to the 16-px cell grid (board origin x=40, y=2).

Findings
- Logic rate is 60 Hz; a mouse moves **1.6 px per frame = 1.5 world units per tick** (cell 16 px = 15 units): identical speed to Android/iOS. Sprite position = p0 - floor(1.6 k) (sub-pixel accumulation), measured on one mouse over 60 frames.
- **Puzzle stage 1 ("Where to go?") with one arrow placed at cell (6,4) pointing up: the GBA run removes 30 mice at frames 62, 72, ..., 822 (30 events across 820 frames); the C++ simulation with the same arrow predicts 61, 71, ..., 821 - identical sequence, constant +1 frame (the sprite disappears one frame after the logic removes the mouse).** This exercises serpentine walls, edge wrap, arrow turns and rocket entry.
- Not yet done: automating arrow placement for more stages (needs the panel order per stage), cat/hole cases, battle mode (GBA has 4P/team battle with CPUs and a roulette: "Night Time!" event seen in the title demo), speeds in battle options, fixed-point details. The harness runs the real game so these are now measurable.

## CPU-AI search, first pass (2026-11-13) - not located yet
Method: boot the ROM in the harness with no keys; the title screen runs a CPU battle demo (about frames 2100-3000; four CPU players, roulette "Everybody Move!"). Findings: the ROM's LCG (multiplier 0x41C64E6D, increment 0x3039, returns the 15-bit result) is the function at 0x080054F4 (Thumb). In 300 demo frames it is called from only three places: 0x08002704/0x08002714 (about 4 calls per frame: an effect/particle spawner, not the AI), and 0x080098DA (5 calls: a two-way direction choice from a delta, probably a cat or mouse turning decision). The CPU arrow placement is therefore not driven by this RNG in that window, or it is rare; the real placement routine was not found. IWRAM at 0x03000EC0.. is the sound mixer (about 40% of executed instructions), 0x08009000-0x0800A5FF carries the gameplay logic. A scan of RAM for the 108-tile and wall bytes of every one of the 2,566 exported puzzle boards found no copy during the demo, so the demo's battle board is stored in another format than the puzzle boards (the battle stages are not in the export). Next: log the callers of the per-frame object update to find the four CPU cursors, then watch which function writes the arrow objects.

## GBA arrow placement and CPU code located (2026-11-13)
Found by comparison, no emulator beyond the Unicorn harness: placing an arrow with the A button in Stage Challenge (a 1P mode that runs in the harness; 4P/Team Battle need a link cable and stop at a cable error) and diffing which code writes RAM in that frame against a frame without input gave the arrow primitive **`0x08004EF0`** (Thumb; r0 = player/cursor record with the player id at +3, x halfword at +8, y halfword at +0xc; r1 = direction). It allocates the arrow object (exec function 0x08005045, life counter 0x258 = **600 ticks**, the same arrow life as the other versions), keeps a ring of **3 arrows per player** (when the third is placed the oldest is shifted out), and writes `0x60 | player | direction` into the field map. In the title demo the CPU players reach it from exactly one place: **`0x08009844`**, a wrapper that reads the CPU's chosen target from a 16-byte per-player record at `0x03000220 + 16*player` (x at +0xc, y at +0xd, direction at +0xe), checks that the target cell is empty with `0x08009464` (field map at 0x030029A0, 27 bytes per row, cell (x, y) at lattice (2x+1, 2y+1), empty = high nibble zero) and then calls 0x08004EF0. The CPU decision code is the block **0x08009000-0x0800A5FF** (about 3% of executed instructions each for 0x0800A4C0 and 0x08009280): `0x080094A0` is a heat-map scan that keeps the two best cells (value halfword at 0x03000500/0x03000502, cell at 0x03000504-0x03000507) over a table of 3-halfword entries at 0x0300028E; `0x08009568` dispatches on the low 2 bits of the byte at 0x03000274 to `0x080091C4`/`0x080094A0` with the tables at 0x03000350 and 0x03000428. The structure matches the task-pool/heat-map design of the other versions. Not yet read: the per-player think state machine (0x080095D8 onward, 0x0800990C, 0x08009A20, 0x0800A4C0), how the heat map is built, the delay/timing, and the random source (the LCG at 0x080054F4 is not called by this code in the demo, so difficulty variation may come from elsewhere). Disassembly of the block: `local/gba_ai.txt` (derived, not committed).
