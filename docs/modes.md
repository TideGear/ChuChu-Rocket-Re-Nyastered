## Observations
- The puzzle editor and the connection-type menu appear only in iOS 1.1.x and Android, not in 1.0.2 or HD 1.0.
- Android has two classes no iOS build has: `DownloadScreen` and `NetNameDispFontScreen`. `FI_GetEdDlPuzzleFromVM`
  is a stub returning 1, so the Dreamcast downloaded-puzzle path appears present but disabled. Needs a closer look.
- The Android build contains network-battle classes but ships no transport (see the netplay notes).
- `NetFourBattleGameScreen` exists in every iOS build, including 1.0.2 and HD 1.0.

## Local multiplayer input (app, 2026-11-13)
Battle mode supports 1-4 human players: `CCR_HUMANS=1..4` makes that many slots human (the rest CPU level 3; levels via the 5th argument). Mouse = player 1 (click places, click again rotates); keyboard sets WASD+Q (P1), IJKL+U (P2), keypad 8/4/5/6+0 (P3); gamepads in connection order (D-pad moves the cursor, Dreamcast-style face buttons Y/A/X/B place up/down/left/right). ## Challenge mode, first reading (Android 1.15, 2026-11-14; not implemented, the rules below are NOT yet derived)
- Data: 25 challenge stages (`CHSTAGE25.DAT` on the Dreamcast), saved per stage as a best time (`Data::getChallengeTime`, 25 words), cleared flags (`isChallengeCleared`, `clearChallenge`), `isChallengeFinalAvailable` (all earlier stages cleared: the 25th stage, index 0x18, is the final one) and `isChallengeClearedAll`.
- `ChallengeInit` (0x30a6c) sets `GA_SetGameType(2)` and `Core::changeGlobalMode(0xe)`. `ChallengeGameScreen::process` dispatches the screen states 0x3e (load), 0x3f (fade), 0x40 (play: calls `ChallengeLoop` unless paused), 0x41 (exit); the play state reads `getChallengeInternalMode()` and treats values 5 and 6 specially (a countdown field at +0xa20 that triggers a handler).
- `ChallengeLoop` (0x30388, 7-phase jump table, 1,574 bytes) mixes the puzzle and battle engines: its phases call `SC_InitScoreBoard`, `RO_StartRocket4Manager` + `CU_StartCursorCh0213Manager` (a battle-style set-up) or `RO_StartRocketPzManager` + `MO_PutMousePuzzle` + `CA_PutCatPuzzle` + `CU_StartCursorCh02Manager` (a puzzle-style set-up), `GE_StartGenerator4Manager`, `GE_SetProhibitGenerator`, `GE_SetCatFever`, `RL_StartRoulette4Manager`, `TI_SetBCDTimer`/`TI_CountDownBCDTimer` with the same 5..0 s tick sounds as the battle, `CA_CatHallIn`, `MO_GetEatenMouse`, `MO_GetRocketMouse`, `MO_GetKilledMouse`, `CA_CatRocketIn`, `RO_GoGoRocketPz`, `clearChallenge` + `save`, and `GA_GetStageNum() == 0x18` branches; the stage's challenge type (`GetChallengeType`), mouse count, cat/team scores (`getChallengeCatScore(i)`, `getChallengeTeamScore(i)`) and internal mode (`getChallengeInternalMode`, values 3, 5, 6 seen in input code) select between those set-ups. Human arrow placement in the challenge is allowed only in internal mode 3 (`ChallengeGameScreen::handleInput` -> `AR_PutArrow(0, ...)`).
- To do: decode the seven phase bodies and the table that fills type/internal mode per stage, then port and diff-test against the Android code like the battle.

### Challenge set-up, decoded further (Android 1.15 `ChallengeLoop` phase 0 at 0x304ac, 2026-11-14)
- The jump table of `ChallengeLoop` (at 0x7332c): phase 0 -> 0x304ac (set-up), 1 -> 0x30552, 2 -> 0x305a2, 3 -> 0x3065a, 4 -> 0x305c4, 5 -> 0x305f8, 6 -> 0x30460 (running; the common running code at 0x30428 steps the collision/task server, counts a 0x78-tick intro and plays song 0xc when it ends).
- Phase 0: `setDeformerFlag(1)`, `GA_OnGameFlag`, `SmpTskInit`, `createPlayfield` with the stage (`FI_GetFIPSptr(2, stage)`), `GA_SetCharaSpeed(0)`, `FI_InitFieldCollision`, then **the challenge type is `stage index mod 5`** (`__aeabi_idivmod(stage, 5)`, stored as the internal mode read by `getChallengeInternalMode`), except the last stage (index = `GA_GetStageNumberTotal(2) - 1` = 24), which branches to its own set-up (0x308ac); the countdown is `TI_SetBCDTimer(0x3000)` (30 s by the BCD layout noted in rules_events.md).
- A second jump table (at 0x73348) by internal mode: modes 0, 1, 2 -> 0x3078c (`RO_StartRocketPzManager`, `MO_PutMousePuzzle`, `CA_PutCatPuzzle`, `CU_StartCursorCh02Manager`, `AR_StartArrow4Manager`: puzzle-style set-up with the stage's mice and cats), mode 3 -> 0x3077a (`SC_InitScoreBoard`, `RO_StartRocketPzManager`, `CU_StartCursorCh02Manager`, `AR_StartArrow4Manager`: only rocket, cursor and arrows, the generator supplies the rest), modes 4 and 5 -> 0x30700 (`SC_InitScoreBoard`, `RO_StartRocket4Manager`, `CU_StartCursorCh0213Manager`, `AR_StartArrow4Manager`: battle-style with four rockets and four cursors). Later in the phase the generator (`GE_StartGenerator4Manager`, `GE_SetProhibitGenerator`, `GE_SetCatFever`) is started for modes 3, 4 and 5 only, and `RL_StartRoulette4Manager` appears in one branch.
- Running phase: the 5..0 s tick sounds `ChuSECall(0x13 - seconds)` as in the battle, at 0 `PA_SetPauseDisable`, `GA_OffGameFlag` and a result function (`FUN_0002fb54`) chosen by internal mode (value 4 goes to 0x30a00, values above 4 to 0x3096a).
- Still to decode: what ends each mode successfully (the rules for 0..2 vs 3 vs 4/5, score targets `getChallengeCatScore` / `getChallengeTeamScore`, mouse count `getChallengeMouseCount`), the stage-24 set-up at 0x308ac, and the result functions. No Challenge code is ported yet.

### Challenge win/lose branches (Android 1.15 `ChallengeLoop` running phase, read from the disassembly 0x30428..0x30a20; the mapping of each branch to a stage type is NOT yet established)
- Outcome functions: success `FUN_0002fb24` (0x2fb24: `PA_SetPauseDisable`, `GA_OffGameFlag`, `ChuSECall(0x15)`, `ChuSECall(0x1c)`, phase := 4), failure `FUN_0002fb54` (0x2fb54: same two calls, `ChuSECall(0x1b)`, phase := 6, input data 0 := -1). Phase 4 (0x305c4) and phase 5 (0x305f8) then run the result display (`clearChallenge(stage, BCD time left)` + `save`, `isChallengeClearedAll`, random bonus value from the sum of the 25 best times, the 25th stage's special path) and phase 6 the fail return.
- Timer: `TI_CountDownBCDTimer` each tick except while the roulette runs in internal mode 5; at 5..0 s the tick sounds play; at 0 the game ends: modes 0..3 -> failure (`FUN_0002fb54`); mode 4 -> success if score field +0x30 > +0x34 (0x30a00), else failure; mode 5 -> success if field +0x20 > +0x24 (0x3096a), else failure. The score-board object is the one behind GOT slot 0x3a4.
- Mouse-based branches seen: (a) rocket mice count equals the stored target (`MO_GetRocketMouse` == value at +8 of the mode block) -> `RO_GoGoRocketPz` + success; a killed mouse (`MO_GetKilledMouse`) or a cat entering a rocket (`CA_CatRocketIn`) -> failure with `FocusInit` on the offender and `GA_SetCharaSpeed(0)`; (b) `MO_GetEatenMouse` differs from the stored count -> failure (0x309bc: `ChuSECall(0x1b)`, `ChuSECall(0x1c)`, phase := 5); a cat `CA_CatHallIn` (cat in a hole) -> failure with focus; `MO_GetHoleInMouse` is checked too; (c) score field +0x30 non-zero and +0x34 zero -> success (the generator modes). Which of these belongs to which stage type (mod 5) is still to be mapped.

### Challenge: stage type -> rule (Android 1.15, third jump table of `ChallengeLoop` at 0x73360, read 2026-11-14)
Phases: 0 set-up, 1 intro banner (waits for a tap/flag or 360 ticks, then `ChuSECall(0x10)`), 2 ready/go countdown (sounds 0x11 at 36/72/108-tick marks: values 0x48, 0x6c, 0x24 of a counter), 3 play, 4 success display (210-frame counter, then phase 5), 5 result (`clearChallenge(stage, BCD time left)`, `save`, tap, next stage = (stage + 1) mod 25, the last stage branches to the final/ending path), 6 failure display. In phase 3 the stage type (stage index mod 5) selects the check:
| type | check each tick | outcome |
|---|---|---|
| 0, 1 | `MO_GetRocketMouse()` equals the target count stored in the mode block (+8) | success (`RO_GoGoRocketPz`); a killed mouse (`MO_GetKilledMouse`) or a cat entering a rocket (`CA_CatRocketIn`) -> failure |
| 2 | `MO_GetEatenMouse()` equals the target stored in the block (+8) | success (phase 5, sounds 0x1b, 0x1c); a cat falling into a hole (`CA_CatHallIn`) or a mouse in a hole (`MO_GetHoleInMouse`) -> failure |
| 3 | player score (score object +0x00) >= 100 | success (score clamped to 100, `RO_GoGoRocketPz`) |
| 4 | score fields +0x30 non-zero and +0x34 zero | success; at time out success if +0x30 > +0x34, else failure |
| 5 | roulette battle: the timer does not run while the roulette spins | at time out success if +0x20 > +0x24, else failure |
Time out in types 0..3 is failure. The meaning of the score-object fields (+0x00, +0x20/+0x24, +0x30/+0x34) and the target values come from the stage data and are not yet mapped; the success/failure labels of the sound ids are inferred from which function sets phase 4 (success) or phase 6 (failure).

### Challenge input and targets (Android 1.15 `ChallengeGameScreen::handleInput` and `ChallengeLoop` phase 0, read 2026-11-14)
- **Target counts:** for the types that use the puzzle set-up the target stored in the mode block (+8) is the return value of `MO_PutMousePuzzle()`, i.e. the number of mice the stage puts on the board; the rocket-count and eaten-count rules above compare against it.
- **The player does not place arrows in most Challenge types.** `handleInput` (touch down/up/move, pause buttons) only drives the arrow origin/preview/`AR_PutArrow` when `getChallengeInternalMode() == 3` (so the arrow-placing type is stage index mod 5 == 3). The other types are choice or timing games: in type 1 a tap sets input flag 1; in types 5 and 6 two on-screen buttons (rects 0xe and 0xf) choose one of two answers (`Input::setData(0, 0 or 1)`, then input flag 2 or 8) and the tap position is remembered; types 0, 2 and 4 take no tap beyond pause. The checks in `ChallengeLoop` read those flags (`getFlag(8)`, `getFlag(2)`, `getFlag(1)`, `getFlag(4)`), so Challenge is a set of watch-and-answer scenarios on top of the puzzle/battle engine, not a plain puzzle: porting it needs the flag handling of each type in the loop (0x3047c..0x304aa shows flag 8 and flag 2 handling with `ChuSECall(2)` and `setData(10, 1)`), which is not decoded yet.

**Correction (same day, after reading the loop's flag handling):** the statement above that types 5/6 are "choice games" is not established. In `ChallengeLoop` the input flags are used by the screens around play: flag 1 skips the intro (phase 1) and advances the result (phase 4/5 taps), flag 8 and flag 2 are the failure screen's two buttons (flag 8 restarts the stage: `[phase] := 0` with sound 2; flag 2 quits: sound 2, `setData(10, 1)`). `ChallengeGameScreen::handleInput` sets those flags from taps/button rectangles (0xe/0xf are the two failure-screen buttons). What is firmly read: arrows are placed only when stage index mod 5 == 3; for the other types `handleInput` has no gameplay input, and their set-ups use `CU_StartCursorCh02Manager`/`CU_StartCursorCh0213Manager` (cursors for characters 0 and 2, or 0, 2, 1 and 3, that is most likely CPU-driven cursors), so these types appear to be scenarios in which the computer players act and the outcome is checked, with the player's role (watching, or tapping at a moment) still unknown. Treat this as unresolved; no Challenge code is written until the cursor manager and the CPU hookup for these types are read.
Second correction: `CU_StartCursorCh02Manager` (0x2b1c8) creates the cursor task for player 0 and, when the player-count global is above 1, player 2 (the same cursors the puzzle uses; `Ch0213` creates all four), so the cursors are the human players' cursors and not CPU-driven ones as guessed above. How the types other than mod-5 == 3 let the player act (the touch handler only reads arrows in type 3) remains unexplained, which means the next step must be a runtime trace (running `ChallengeGameScreen` under the Android emulator harness with injected touches) instead of more static reading.

### Challenge: runtime trace of the original's phase machine (Android 1.15, 2026-11-16, `tools/oracle/challenge_probe.py`)
`challenge_probe.py <stage> [frames]` runs `ChallengeInit` (0x30a6c) and then `ChallengeLoop` (0x30388) once per frame under Unicorn with no input; the mode block is at ghidra 0x17b614 (+0xc phase, +8 target). Render, sound and Flurry calls are stubbed (`challenge_patches.txt` lists the stubbed functions, found by running until a fault; Unicorn caches translated blocks so patches go in before execution). The stage struct comes from the Dreamcast `CHSTAGE25.DAT` converted with the battle probe's `ascii_stage`, written into `FI_GetFIPSptr(2, stage)`, and the stage index goes in the first argument of `GA_SetStageNum` (`GA_GetStageNum` reads word +4). The mobile Challenge boards are byte-identical to the Dreamcast ones (docs/stages.md, setup-verified export), so these are also Android's own boards; the targets and timings below are what the Android code produces for them. The runtime loader that fills the type-2 stage array (`FI_GetFIPSptr` stride 0x15c) was not traced, which is the only open point about the data.
- Phase timing, identical for every stage: phase 1 intro lasts 362 ticks, phase 2 (ready/go) 108 ticks, play (phase 3) starts at tick 470 and times out after **1800 ticks (30 s)** into failure (phase 6).
- Every stage uses the puzzle set-up: `RO_StartRocketPzManager`, `MO_PutMousePuzzle` (its return value is the target stored at block +8), `CA_PutCatPuzzle`, `CU_StartCursorCh02Manager` and a BCD timer (`TI_SetBCDTimer`); stage 0 additionally creates its objects through a shorter path. So a human places arrows (cursor manager) in every type in the Android code, not only type 3.
- Target mouse counts by stage (type = stage mod 5; types 3 and 4 have no mouse target): 0:26, 1:24, 2:27, 5:95, 6:32, 7:44, 10:18, 11:36, 12:60, 15:20, 16:24, 17:24, 20:12, 21:26, 22:15; types 3 (stages 3, 8, 13, 18, 23) and 4 (stages 4, 9, 14, 19, 24) report 0.
- With no input the first failure comes at tick: stage 1 638, 4 986, 14 1481, 15 611, 16 951, 17 576, 21 636, 24 517 (a killed mouse, a cat in a rocket or a hole, or the type-4 comparison); every other stage runs the full 1800 ticks to the time-out failure.

### Challenge stage data: loader search (Android 1.15, 2026-11-16, not found)
`FI_GetFIPSptr(type, stage)` (0x2ddd0) returns `table[type] + stage * 0x15c` for types other than 3 and 4 (types 3 and 4 use fixed offsets in the same block); the pointer table is statically initialised at ghidra 0x79020 and slot 2 (Challenge) points at 0x163b00, a `.bss` array of 25 stages (the library file ends below that address, so it is filled at run time). Its only callers are `FI_GetFIPNow`, `ChallengeLoop`, `PuzzleLoop` and `createPlayfield`, none of which fills it, and no code refers to the array address through a pc-relative literal, so the filling goes through a GOT reference. The 25 Challenge boards are resource record 540 (11,925 bytes, 25 x 477-byte ASCII maps) of the main pack (record 541 is the Battle set); the literals 540 and 541 occur in several functions but are offsets, not the loader. Arrow stock bytes live at stage offset 0x15c (the ASCII maps carry none), so how the Challenge stock is produced is still unknown. Next probe: run the app start-up in the harness, or hook stores into 0x163b00..0x165cfc, or search the GOT for the symbol that owns 0x163b00.

**Loader found (same day).** `FI_LoadMaps` (0x2e7b8) calls `FUN_0002e6cc` (0x2e6cc) twice: once for the Battle array (resource 0x129) and once for the Challenge array at +0x21fc (resource 0x128, 25 stages at stride 0x15c, 0x1dd bytes of ASCII per row-block step). The converter reads the 25 x 19 text map row by row: for each cell it writes the tile byte at stage offset +0 (`'7'` becomes 0x11, `'9'` becomes 0, any other character becomes `ch - 0x40`) and, on the alternate rows and columns, the wall bytes at +0x6c (`'1'` becomes 1, else 0). **Nothing is written at stage offset +0x15c, so the Challenge arrow stock is zero in all 25 stages**: the player has no arrows to place from a stock, which fits the earlier reading that `ChallengeGameScreen::handleInput` only drives arrow placement in type 3 (a battle-style set-up with cursors). The harness struct (tiles, walls, zeros elsewhere) therefore equals what the original builds, and the targets, timings and rules above stand for Android's own data. Open: what the human does in types 0, 1, 2 and 4 with no arrows (candidates: the cursor manager moves a character, or the stages are watch-only scenarios driven by the boards' own preset objects), and the 20 and 20 counters of type 4.

**Human role in Challenge (same day, set-up call traces `CALLS=1 challenge_probe.py <stage>`).** Every type calls `AR_StartArrow4Manager`, the battle arrow manager (free placement, no per-direction stock), together with `CU_StartCursorCh02Manager` and `CU_CursorCons`, not the puzzle arrow manager `AR_StartArrowPzManager`; so the zero stock of the stage struct does not limit the player, who places arrows with the battle rules. Per type: types 0 and 1 (stages 0, 1, 5, 6, ...) use `RO_StartRocketPzManager`, `MO_PutMousePuzzle` and `CA_PutCatPuzzle` (stages whose type is 1 and 2 also call `CA_PutCat`/`GA_GetCatSpeed`, so their cats are created through the battle cat path); type 2 the same with the eaten-mouse rule; type 3 adds `SC_InitScoreBoard` and creates no mice or cats from the stage (a score race fed by the generators); type 4 is a four-player battle set-up (`SC_InitScoreBoard`, `RO_StartRocket4Manager`, `CU_StartCursorCh0213Manager`, `RO_GetRocketFieldGrid`, `CU_SetCursorControlByParameter` for the computer-driven cursors) whose two counters (words 12 and 13, 20 and 20) fall as the sides lose characters. With no input the cats of stage 2 eat 19 of the 27 mice by themselves and no mouse reaches a rocket in the type 0 stages (counters read at the end of each run: rocket 0 for stages 0, 1, 2, 5, 10, 15, 20; eaten 2 in stage 1, 19 in stage 2). So Challenge is the battle arrow game on puzzle boards: the port can reuse `BattleGame::placeArrow` and the existing cat and mouse tasks, with the stage-type rules of the table above and the intro, countdown and 1800-tick limit. The remaining work is the per-type entity set-up (which `CA_PutCat` and `MO_PutMouse` creation paths differ from the puzzle ones), the type 4 side counters, and the result/save path.

**Stage 24 is not a plain type 4 (2026-11-16 probe).** With words 12 and 13 of the score array held at 5 and 3 from frame 471 to 520 (so neither type 4 trigger can fire), stage 24 still reaches the failure phase at frame 517, and a poked "success" counter pair at frame 480 does not prevent it either; stage 4 (the same type) accepts the poke and succeeds at 481 with `clearChallenge(4, 0x2932)`. So the last stage has its own set-up and failure rule (the `0x308ac` branch noted above), and its 60 second limit, its two counters and its trigger are not yet understood. Stages 3, 8, 13, 18 and 23 (type 3) and 4, 9, 14 and 19 (type 4) remain to be ported on the battle engine.

**Stage 24 decoded (Android 1.15 `ChallengeLoop` 0x308ac, 0x30946, same day).** The last stage's set-up writes internal mode 5 into the mode block (+4), calls the timer set function 0x2ef48 with 0x10000 (a one minute BCD timer, matching `clearChallenge`'s 60 second limit for stage 24), and in mode 5 starts the battle generators (`GE_StartGenerator4Manager`, 0x34b08) and the roulette manager (`RL_StartRoulette4Manager`, 0x3cd90) after the four-player rocket and cursor managers of types 3 and 4 (mode 4 starts the generators with prohibit mask 0xf and `GE_SetChu2Fever`-style settings via 0x34ac8, mode 3 starts them with mask 6). So stage 24 is a one-minute roulette battle against the computer players with the time-out rule "success if score +0x20 is greater than +0x24" from the table above, and it fails in the probe at frame 517 because the harness does not drive the timer, the CPU cursors or the roulette like the app does (the words +0x20 and +0x24 read 14 and 114 at frame 600). Porting stage 24 therefore means a one-minute battle on the battle engine with the roulette running, a player against the opposing side, scored by those two words; the stage 3, 8, 13, 18 and 23 set-up is the battle engine with mask 6 (golden mice off), and the type 4 stages use mask 0xf and the +0x30 and +0x34 counters. All of these still need the harness extended with the app's CPU and timer calls before a diff is possible.

### Puzzle Edit: first reading (Android 1.15 `Editor::convertField` 0x2d0ec, 2026-11-16; static only, nothing ported or verified)
`convertField(PzStageData*, arrowPos*, editorData*)` turns the editor's per-cell words (`editorData`, one 32-bit word per cell, the object class in bits 0x f00) into a puzzle stage struct: it clears the tiles (0x6c bytes) and walls (0xed bytes) and the four stock bytes at stage offset 0x15c..0x15f, copies up to 0x15 bytes of the title from `editorData + 0x1b0` to stage offset +0x160 (stopping at the terminating zero and padding with zeros), and walks the 12 x 9 cells: class 0x100 counts a rocket (byte 0x15e) and records an `arrowPos` entry of type 2, class 0x300 counts one more of the byte at `DAT_0002d3e8` (0x15d) with type 1, class 0x400 counts one of the byte at `DAT_0002d3ec` (0x15f) with type 3; the remaining classes write the tile byte by the low nibble (1 = a cat whose colour is the next nibble: 0x10 gives tile 0xf, 0x20 tile 0xd, 0x30 tile 0xe, 0x40 tile 0x10; 3 = a mouse tile 1 or a rocket...), with the wall bits handled after. The other editor entry points are `loadLevel` (0x2d59c), `sendLevel` (0x2cf80, uploads a level), `saveEditStage` (0x2ce6c), `setEditStage` (0x2cf30), `create`/`destroy` and three HUD renderers (`renderEditorHudPad`, `...Phone`, `...Retina`); the editor exists only in iOS 1.1.x and Android (docs/modes.md header table). A port needs: the cell word layout, the tile and class mapping above (finish decoding), the validity rules the editor applies before a level can be saved or sent (not yet read), the save slots and sharing format, the editor HUD and tool palette art, and a differential test of `convertField` against the emulated original in the style of `players_input_diff.py`.

**Puzzle Edit: `convertField` verified (2026-11-16, `tools/oracle/editor_convert_diff.py`, 500 random editor boards, 0 mismatches against the emulated Android 1.15 function).** Corrections and details to the first reading above: the editor data is 12 x 9 little-endian 32-bit cell words (row stride 0x30), then the zero-terminated title at +0x1b0. Cell word: bits 8 to 11 are the object class (0x100 rocket, 0x200 an arrow of direction 0, 0x300 direction 1, 0x400 direction 3; other values count nothing); the low byte gives the tile: low nibble 1 is a cat (high nibble 1..4 gives tiles 0xf, 0xd, 0xe, 0x10), 2 is a mouse (1..4 gives 0xb, 9, 0xa, 0xc), 3 is a rocket (tile 1) and 4 is a hole (tile 0x11); a cell carries both its class and its tile bits independently (the class only feeds the counters and the arrow list). Walls: bit 12 is the cell's north wall (horizontal wall row r), bit 13 the south wall (read from the bottom row only, as horizontal wall row 9), bit 14 the west wall (vertical wall column c), bit 15 the east wall (read from the last column only, as vertical wall column 12); the stage layout is tiles at +0 (108 bytes), horizontal and vertical walls interleaved from +0x6c with a row stride of 25 (`hw[r][c]` at +0x6c + 25r + c, `vw[r][c]` at +0x78 + 25r + c). Stock bytes: +0x15c counts class 0x200 cells, +0x15d class 0x300, +0x15e class 0x100 and +0x15f class 0x400 (so the editor's "arrows" are the level's per-direction stock, and class 0x100 is counted into the third byte); the title is copied to +0x160 (at most 21 bytes, stopping at the terminating zero and padding with zeros); the optional arrow list receives one 8-byte entry (x u16, y u16, type u32 = 0, 1, 2 or 3 for the classes 0x200, 0x300, 0x100, 0x400) per class cell in row-major order, and the function returns how many. Bytes 0x159 to 0x15b and beyond 0x174 are not written. ### Puzzle Edit: storage and sharing, first reading (Android 1.15 `saveEditStage` 0x2ce6c, `setEditStage` 0x2cf30, `loadLevel` 0x2d59c, `sendLevel` 0x2cf80; static, 2026-11-16)
- **Slots:** a level slot is 0x2d4 (724) bytes. `saveEditStage` copies the working buffer (the editor state: board words, title at +0x1b0 and the rest up to 0x2d4) into slot `Editor::stage_num` of the slot array and then builds a file path string (the app's data directory plus a fixed name and the number, for the persisted copy); `setEditStage(n)` makes slot n current and copies it to the working buffer; `Editor::create` allocates the working buffer, copies a 0x1b0-byte template (an empty board) into it, runs `initializeCRC` and formats the default title with "%d" (stage number 1). `loadLevel(n)` builds the file name for level n; the file read itself happens in the caller.
- **Sending:** `sendLevel(n)` takes the 0x17c-byte puzzle stage struct (`FI_getStagePtr`, the result of `convertField`) and computes its CRC with `calculateCRC`; if the level has a recorded solution (`move count > 0`, the per-level move list at 0x80 bytes per level, up to the stored count) it encodes every move as hexadecimal characters through a lookup table (two nibbles per byte: 6 characters per move from three 16-bit fields... the field meaning is not decoded), terminates the string and formats the request text as "<crc>" and "<moves>" with a format string; the actual upload is network code (iOS and Android only). So a shared custom puzzle is the stage struct plus its CRC plus the solution moves, and the server checks that the solution solves the level (the editor therefore makes the author play the level before sending: not yet read).

**Puzzle Edit sharing format decoded (2026-11-16, static, same functions as above).** The hex lookup table of `sendLevel` is the lowercase string `0123456789abcdef`; each solution move is an 8 byte record of which three fields are written, each as two hex characters (high nibble first), so six characters per move, in field order; the request text is `http://www.binaryhammer.com/ccrlvls/ccr_lvlup.php?crc=%.8x&arw=%s&lvl=` with the CRC-32 of the 0x17c byte stage struct and the move string, followed by the level data itself (appended by the caller; not read yet). The server is the original developer's and is not used by the port; the port's `editorSolutionHex` (game/core/editor.hpp) produces the same move string for the planned file-based sharing. The three fields are presumably the arrow's x, y and direction (the editor stores the level's author solution as arrow placements); this needs confirming against an editor session in the emulator before the file format is fixed.
