## Android 1.15 `TitleScreen::render` (0x67...; constants read from the literal pool, 2026-11-13)
Draw order: (1) full-screen tilemap/background texture (offset -64 on one device class, (-130, -100) on another, 0 otherwise); (2) a background sprite that orbits: x = center_x + cos(angle * 0.0174533) * radius - w/2, y = center_y + sin(...) * radius - h/2, angle advances with the screen's timer (the +180 deg phase for the second term); (3) the logo texture at x = 208 (three device classes) or x = 12, y = 28 (small-screen layout); (4) in game state 0xC, a prompt texture ("TAP THE SCREEN!") at (368, 504) on two device classes, (368, 544) on the third, (132, 251) on the small layout, drawn only while a timer is <= 333,333 (microseconds: a blink, 1/3 s on); (5) in states 0xB / 0xD a black full-screen rectangle whose alpha = timer / 500,000 * 255 (a fade of 0.5 s). The coordinates imply a 1024x768 landscape layout for the large-screen classes, so the menu layer needs its own logical resolution (1024x768, plus the 480x320-class phone layout) separate from the 768x640 gameplay view. Still to read: `TitleScreen::process` (state machine, timers), `MenuScreen::render/process/handleInput`, the texture-index -> sprite-sheet table (`AppData::bindTextureSpace`).

### `TitleScreen::process` / `init` (Android 1.15)
State machine (game state numbers): `init` loads the tilemap resource 0x124 (small layouts), zeroes the timers and enters state **0xB** (fade-in: the timer counts DOWN to 0, the black rect alpha = timer / 500,000 * 255); at 0 it enters **0xC** and starts song 0 (title wait: the orbit angle advances every frame, wraps at a threshold, the prompt blinks); a tap moves to **0xD** (fade-out: timer counts UP; at the threshold the screen leaves to state **5**, the menu, or **6** when downloadable levels are new (`Data::getNumNewDlLevels() > 0` and the first-run flag is clear)). The DC-style "press start" and the logo drawing are the same in spirit on the Dreamcast.

### `MenuScreen::render` (Android 1.15) - what it needs
Per device class (three layouts) it draws: the tilemap background (`AppData::drawTilemap` with a per-layout offset), then the main-menu panel texture at (this+0xe0, +0xe4) + the sprite's own offset when the menu is not in its transitional state, then a "cat/rocket" decoration at a layout-specific position, then two **speech bubbles** (`Render::drawBubble`: one with the localized help string chosen by whether the tutorial is cleared (`Data::isTutorialCleared`) and a second bubble with a text field), a fade rectangle in states 0x11 / 0x13 (alpha from a timer), and for each menu entry the entry texture plus its text (`BHLib_PrintString` with the localized string from the resource text table, centred in the entry box, with a shrink factor for long names). So rebuilding it faithfully needs (a) the BHLib resource/tilemap formats (`BHLib_GetRawResource`, `drawTilemap` tile data resource 0x124 etc.), (b) the texture-space/sprite table (which sprite each id draws, with its size/offset fields at +0x14/+0x16/+0x1c/+0x1e), (c) the localized string tables (EN/FR/DE/ES/IT/JA) and the font drawing with its metrics, (d) `drawBubble`. The sprite sheets we already extract (`main_png`) contain (b)'s images; the tilemap and string tables still have to be extracted and decoded, then a data-driven UI layer written.

## Tile maps decoded; full-resolution backgrounds (2026-11-13)
Format (from `AppData::drawTilemap`): record = 5 x int32 (columns, rows, tile width, tile height, tile count) + one uint32 per cell (bits 0..27 tile/frame index into the atlas frame table, bit 30 flip X, bit 29 flip Y). The atlas is a 4-byte/pixel texture (8-byte (w, h) record + 65,520-byte chunks) whose frame table is the record after the chunks (u0 v0 u1 v1 + 5 floats per frame, 36 bytes); each frame carries a 1-pixel padding border around the tile. `tools/export_tilemaps.py` assembles them. Result for the iPad HD pack (`ccrpad`): four **1024 x 768** backgrounds from 8 x 6 tiles of 128 x 128: record 877 = title (blue planet with the orange cat, (c) SEGA, TM), 878 = the ringed-planet/stripes background, 879 = the pale-yellow rocket pattern (the menu background), 880 = the molecule pattern. These are the highest-resolution versions of the backgrounds (the phone set has 484 x 322 images of the same art). The same tile-map records exist in the Android and iOS 1.1.2 phone packs (50 x 50, 64 x 75, 96 x 96, 128 x 128 tiles) and still have to be exported. The iPad title/menu layouts (device class 3) need the matching element positions from the code's literal tables for that class; the app still draws the phone layout with the smaller art.

## Image ids of `Render::drawImage` (2026-11-13)
`Render::drawImage(id, frame, x, y, flags, scale, y2)` reads the loaded-texture array `AppData[(id + 6764) * 4]` (texture slot pointers filled by `putTextureIntoTSpace`) and draws frame `frame` of that texture's frame table (36-byte records: u0 v0 u1 v1 + int16 w, h, 64, 64, xoff, yoff; the draw adds the frame's offsets and scale). So **image id = texture index in the combined pack list**: the Android main pack has 142 textures (ids 0..141: `main_png/NNN_*`, the same numbering as the title/menu texture ids), and ids >= 142 (e.g. the pause code's 0x9e = 158) continue into the character pack (`ccrret`: gameplay sprites). Verified on the pause screen: id 0x6d (109) = main file 109 (104 x 34, a button), 0x75 (117) = file 117 (484 x 76, the pause board), 0x68 (104) = file 104 (240 x 68, the win-point markers). Flags: bit 0x2 = anchor right (x - width*scale), 0x4 = flip Y, 0x8 = rotate. Still to do: list every id used by the HUD/result/pause/countdown callbacks with its position per device class, then draw them (the iPad pack has the same textures at the larger size with identical numbering offsets by pack).

## Battle timer (Android `FUN_0002c934`, 2026-11-13)
The timer is a render-node callback: it reads the BCD game time (`TI_GetGameBCDTime`; format 0x0MSS: minutes nibble at bits 16..19? the code uses nibbles at >>16, >>12 and >>8, so the value is 0x00M0SS shifted) and draws texture **0x74 (116)**: frame = minute digit at (X, Y), frame **10 = the colon** at X + W, then the two seconds digits at X + 1.5 W and X + 2.5 W (X, Y, W are per-device HUD metrics stored in the AppData structure at +0xf4, +0xf8, +0xfc, set once at start-up for the device class; not yet extracted). Texture **0x73 (115)** frames 14/15 form the 9-segment "clock hand" gauge drawn while the game flag is 1 (it fills as the BCD countdown runs out, stepping 9 segments). `drawClockSplit` is the same for the split-screen (two-player-per-side) layout. In the 3-minute battle the BCD value is doubled when the round length is 0x3c.

## Battle count banners (Android `BattleCountInit/DrawPriority`, 2026-11-13)
A short-lived task (lifetime counted in ticks; the roulette-start task `RoundCountInit` lives 0x4b = 75 ticks) draws one banner image by mode number 0..5 through `Render::drawImage(id, frame, ...)`: modes 0, 1, 2 = image id **119** frames 0, 1, 2 (scaled by a per-device factor: the three big count digits), modes 3, 4, 5 = image id **120** frames 2, 0, 1 (not scaled by the device factor: round banners). Per mode the y position grows linearly with the tick counter (factors 0.09 for modes 3..5, -0.033 + 4 for modes 0..2 stage 1, -0.13 + 8 for the next group). Triggers in the net-battle loop: `BattleCountInit(3)` + sound 0x7f + `BGM_Change(6, 0x3c)`, `BattleCountInit(4)` + sound 0x7e, `BattleCountInit(5)` + sound 0x7d, `BattleCountInit(0)` at the round start event; which banner is the "3-2-1" and which the "Winner/Draw" is not yet pinned down. (See the correction below: this task is the end-of-round burst/"Draw!" banner.)

## Resource-id tables (Android 1.15, read 2026-11-14)
`AppData::getActualResourceID(id)` (0x681c8) returns `tableA[id]` when the device field (AppData +0x697c) is non-zero (480 x 320 class) and `tableB[id]` when it is 0 (800 x 480); the tables are in .data at file offsets 0x6acb8 (A) and 0x77b08 (B) (GOT slots 0x69954 / 0x696a4, R_ARM_RELATIVE). Examples: A[0x5f..0x75] = 222, 223, 225, 226, 228 ... 255; B[0x5f..0x75] = 314, 315, 317, 318, 320 ... 354. Checked against the extracted `main` pack: these values do NOT land on the texture header records of the `Render::drawImage` images (e.g. B[0x65] = 325 is a 28 x 38 header, B[0x73] = 348 a raw data block), so `getActualResourceID` maps the screens' *resource* ids (tilemaps, raw resources such as 0x11c, 0x124, menu sprites), not the `drawImage` image ids. `drawImage` reads texture descriptors from AppData[(id + 6764) * 4], filled when a screen registers textures (`putTextureIntoTSpace` / `addTSpaceEntry` with the image id). Next step: read the code that fills that descriptor array at start-up (the loader that walks the pack's texture list) to get image id -> texture record; then match 0x67, 0x73, 0x91, 0xaa, 0xad and the other HUD images.

## Image id -> texture: SOLVED from the code (2026-11-14)
iOS 1.1.2 `AppData::loadResources` (0xb1f4) creates all 175 draw images: image i = `BHLib_CreateTexture(pack, getActualResourceID(tex[i]), getActualResourceID(frm[i]))`; `getActualResourceID` (0x8990) uses `_ccrphn_res` for device classes < 6, `_ccrret_res` for 6..9 (retina, the pack the app uses) and a third table for >= 10. Resource ids >= the main pack's record count (978) address the **language pack** `ccrret_<lang>` (id - 978): that is where the HUD images with text live, which is why they were never found in the main pack. Verified on known images: 0x5f arrows -> 645, 0x6a digits -> 729, 0x6b cursors -> 732, 0x69 crowns -> 726 (all match the sheets already in use); 0x73 -> ccrret_en 108 (396 x 117, 24 frames: Pause button, "Computer" tag, HUD panels, rocket icons), 0x67 -> ccrret_en 85 (236 x 244: the puzzle HUD "Start ▼ Dash" / "Cancel" panel, "stage" label, strip pieces). Tools: `tools/extract_ios_locale.py` (language packs), `tools/image_map.py` (writes `image_map.json`). Android uses the same scheme (`loadResources` 0x6b294, tables `ccrphn_res` / `ccra800_res`).

**Answer (read 2026-11-14):** `-[CCRViewController awakeFromNib]` (iOS 1.1.2, 0x4dba8) sets the device class from `uname().machine`: "iPod" 4+ -> 6, "iPhone" 3+ -> 7 (retina, `ccrret` pack + retina layout struct), "iPad" -> **10 only if the bundle resource "ccrpad" exists** (fopen of the path for @"ccrpad"), otherwise 4 (480 x 320 phone layout, `ccrphn` pack); everything else -> 3. The 1.1.2 IPA ships no `ccrpad`, so on an iPad 1.1.2 runs the phone layout and its class-10 layout struct is never used. Consequence for the app: the 1024 x 768 layout it currently draws (1.1.2's class-10 struct) pairs with art 1.1.2 never loads; the coherent original iPad combination is **HD 1.0** (its own binary: `loadResources` 0xdcd8, 160 images, pad table at *0xeb548, the `ccrpad` pack and HD 1.0's own layout struct and image ids), or alternatively 1.1.2 retina (class 6/7: `ccrret` + the retina struct). Plan: switch the playfield/HUD to the HD 1.0 trio (layout struct, image id map, ccrpad art) since the iPad pack is the largest source (asset_quality.md); features missing in HD 1.0 (Puzzle Edit, connection menu) take their screens from 1.1.2 retina.
